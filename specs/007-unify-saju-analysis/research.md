# 설계 조사: 전체 초기화 결정과 요청별 독립 저장

**수정일**: 2026-10-31 | **명세**: [spec.md](spec.md)

## 1. 조사 범위와 현재 결정

현재 저장소의 코드·기존 문서를 근거로 설계를 수정했다. 이번 작업에서 DB 접속·원본 추출·SQL 실행·애플리케이션 변경은 하지 않았다. 현 DB 스키마와 실제 행 수는 운영 전 별도로 확인할 대상이다.

근거는 `SSAju/build.gradle`, `SSAju/CLAUDE.md`, `SSAju/src/main/java/ssafy/SSAju/` 아래 service의 분석·사용량 코드, career의 엔티티·provider·caller·계산기, repository의 이력·쿼터 코드, admin/repository/AdminAnalyticsQueryRepository다. 이전 로컬 DB 조사에서 코드와 스키마 차이가 기록됐으므로 실제 대상 컬럼을 확인해야 한다. 새 라이브러리는 도입하지 않는다.

**결정**: 기존 분석·접근·프로필·피드백·사용량 전체 초기화를 채택한다. users와 인증 데이터만 유지하고 새 구조는 빈 상태에서 시작한다. 사전 피드백 원본 제공·건수 제공·DB 대조·운영자 확인은 삭제의 필수 선행 조건이다.

**근거**: 사용자가 과거 분석을 서비스에 남길 필요가 없다고 확정했다. 과거 자료의 변환·권한 사본·ID 호환·예외 저장 구조가 필요하지 않아진다. 단, 운영자가 삭제 전 원본과 건수를 확인할 수 있어야 한다.

**검토한 대안**: 과거 결과 유지 및 변환은 이번 결정으로 폐기했다. 분석만 삭제하고 프로필/일일 사용량 유지하는 대안도 채택하지 않는다. 사용자가 두 테이블까지 초기화 범위에 포함했다.

## 2. 실행·전략·트랜잭션

**결정**: 트랜잭션 없는 AnalysisService가 기존 세 DTO의 진입점, 인증 주체, 유형별 전략, 쿼터, 기초 정보, 공통 저장을 조율한다. 세 AnalysisType 전략은 기존 계산기·외부 caller·검증을 재사용한다. 성공 결과만 별도 SajuWriteService의 짧은 트랜잭션에서 저장한다.

**근거**: 외부 API 동안 DB 연결을 점유하지 않는 기존 규칙을 지킨다. 컨설팅·궁합이 관운 계산을 사용해도 별도 SAJU 기록을 만들지 않는다. 전략은 사용자·쿼터·저장 정책을 중복 구현하지 않는다.

**검토한 대안**: 장시간 외부 호출 트랜잭션, 전략마다 저장/쿼터 복제, 무검증 Map 요청, 비동기 진행 상태는 채택하지 않는다.

## 3. 프로필·만세력과 동시성

**결정**: 프로필은 빈 상태에서 기본 출생정보 저장 또는 신규 분석 요청으로 생성한다. 만세력은 분석 요청에서 해당 프로필에 없을 때만 생성한다. 프로필의 출생정보 유일 제약과 만세력의 프로필별 유일 제약을 사용한다. FastAPI·공통 계산은 트랜잭션 밖에서 수행하며 프로필·만세력 저장에 분산락을 사용하지 않는다.

**근거**: 기초 정보만 공유하고 결과는 합치지 않는다. DB 유일 제약으로 중복을 막을 수 있어 분산락을 추가할 필요가 없다. 알려진 유일 제약 경합은 실패한 쓰기 트랜잭션 종료 후 재조회하고 다른 오류는 전파한다.

신규 FastAPI의 기둥·천간/지지 배열·일간/오행·태양 보정과 십성/지장간 공통 계산을 ManseData record의 data_json 하나로 저장한다. ID·프로필 FK·시각만 일반 컬럼으로 둔다. 만세력은 개별 필드를 조건 검색·집계하지 않고 프로필로 찾아 전체를 읽으므로 분리 컬럼이 필요하지 않다. 어댑터는 record의 저장값과 프로필로 기존 계산기 입력을 구성하며 재사용에도 유형별 검증을 생략하지 않는다. 외부 호출 횟수의 완전한 중복 제거 기능은 추가하지 않는다.

이전의 기둥·일간 별도 컬럼 및 오행·태양 보정·십성/지장간별 JSON 컬럼 설계는 단일 data_json 결정으로 대체한다. JSON으로 합쳐도 Java record 타입·필수값·배열 길이·허용값 검증은 유지하며 단순한 무검증 Map으로 바꾸지 않는다.

### 기본 프로필과 분석 프로필의 구분

**결정**: `users.user_profile_id`를 NULL 허용 FK로 추가해 기본 출생정보를 저장한다. 생년월일·시각이 같으면 여러 사용자가 같은 프로필을 기본값으로 참조할 수 있다. 실제 분석 프로필은 `saju → manse → user_profile`로 조회하며 결과 소유자는 계속 `saju.user_id`로 직접 관리한다.

**근거**: 분석 전에 기본값 또는 다른 출생정보를 고르는 용도다. 기본값 저장·조회 API를 제공하고 분석 DTO에는 선택한 구체적인 출생정보를 전달한다. 기본값이 없으면 직접 입력하며 분석이 기본값을 자동 교체하지 않는다. 기본값 저장만으로 외부 분석·만세력 생성·쿼터 사용을 발생시키지 않는다.

프로필 출생정보는 생성 후 변경하지 않는다. 기본값 변경은 다른 프로필을 조회·생성해 사용자 참조만 교체하며 공유 사용자와 과거 결과에 영향을 주지 않는다. 분석은 요청 시 확정한 입력을 사용하므로 진행 중 기본값 변경의 영향도 받지 않는다. 초기화 완료 후 새 nullable FK를 추가하고 유지 계정의 기본값은 NULL로 시작한다.

**검토한 대안**: 프로필에 사용자 소유권을 두면 출생정보 공유와 충돌한다. 결과 소유권을 프로필에서 유도하면 같은 출생정보의 타인 결과까지 노출될 수 있다. 공유 행 직접 수정이나 마지막 분석 입력으로 기본값 자동 갱신도 채택하지 않는다.

## 4. 쿼터와 성공 경계

**결정**: 전환 때 daily_api_usage의 모든 행을 삭제한다. 당일 이미 쓴 쿼터도 재설정된다. 이후 DailyApiUsageService의 기존 MySQL 원자적 조건부 upsert·useAffectedRows 설정·Clock 날짜 기준을 유지한다. 컨설팅·궁합 공유 하루 3회이며 관운은 미적용이다.

차감 뒤 기초 정보·외부 호출·검증·저장 커밋 프록시 반환까지 실패하면 원래 usageDate로 restoreQuietly를 호출한다. 저장 커밋 후 응답 조립·직렬화·전송 실패는 복원하지 않는다. 복원 실패의 로그·suppressed 예외와 원래 오류 전파는 유지한다.

**근거**: 사용자 결정에 따른 일회성 사용량 초기화와 전환 이후 쿼터 정책을 구분한다. 캐시 재사용·결과 저장 경합 보상 분기는 없어지고 각 성공 요청은 사용량 1회다.

**검토한 대안**: 기존 사용량 유지, 현재 날짜로 실패 보상, 응답 전송까지 보상 범위 확대는 채택하지 않는다. 프로세스 강제 종료·불명확한 DB 커밋을 해결하는 새 분산 트랜잭션 기능은 추가하지 않는다.

## 5. JSON과 저장된 신규 결과의 안정성

**결정**: Jackson 3 tools.jackson과 기존 JSON converter 지원을 재사용한다. 타입별 record와 schemaVersion=1로 입력·결과를 검증한다. 결과에는 ID를 제외한 완성된 응답 내용을 저장한다.

**근거**: ConsultationMapper의 요약은 현재 연도를 읽으므로 advice만 저장하면 나중에 내용이 바뀔 수 있다. 요청 당시 관운 tuple·사주 프로필·모델·최종 요약을 모두 저장한다. 궁합은 기존 상세 자료와 본체 점수·summary를 함께 저장한다. 조회 시 현재 모델·연도로 재구성하지 않는다.

불변 AnalysisTimeContext의 분석 날짜·연도·월·대상 월 목록을 프롬프트·재시도·검증·조립까지 전달한다. 쿼터 차감 날짜는 별도로 고정한다. 회사 입력은 요청값과 실제 조회/정규화 값을 구분한다. 새 스키마에는 과거 입력 부재용 표시나 과거 요약 생성 절차가 없다.

**검토한 대안**: JSON에 분석 ID 중복 저장, 일부 advice만 저장, 조회 시 현재 코드로 재계산하는 방식은 채택하지 않는다.

## 6. 숫자 ID 유지와 전체 초기화

**결정**: 분석 ID는 BIGINT AUTO_INCREMENT·Java Long·JSON 숫자를 유지하고 새 saju 테이블에서 처음부터 발급한다. 과거 분석은 사전 보고용 추출 후 삭제한다. 신규 ID 발급에 과거 최댓값·시작 번호 보정·번호 경계·호환 매핑을 사용하지 않는다. 예전 URL의 영구 404도 보장하지 않는다. 현재 결과의 소유자·유형 검증은 유지하며 없는/타인/유형 불일치 ID와 관운 대상 피드백은 404다.

**근거**: 전체 초기화 후 과거 분석을 제공하지 않으므로 기존 번호와의 충돌을 피하기 위한 별도 식별 체계가 필요하지 않다. 기존 숫자 API 계약을 유지한다.

**폐기한 대안**: UUID 전환과 과거 최댓값 기반 시작 번호 보정은 적용하지 않는다. 버전별 경로·별도 공개 ID도 추가하지 않는다. 피드백 요청 feedbackType 제거 등 확정된 API 변경은 문서에 정리해 추후 클라이언트에 전달하며 클라이언트 수정·동시 배포 조율은 이번 범위 밖이다.

## 7. 초기화 전 제공 자료와 건수 기준

**결정**: 피드백 테이블 모든 행·모든 컬럼을 원본 그대로 제공한다. 사용자 테이블을 조인하지 않고 가공·마스킹·필터도 하지 않는다. 탈퇴 사용자와 미연결 행도 포함한다. 원본 컬럼명·값·NULL·문자열 줄바꿈·DB 정밀도가 손실되지 않는 로컬 형식으로 전달한다. 별도 집계 자료 때문에 원본 파일에 컬럼을 붙이거나 값을 바꾸지 않는다.

건수는 사주 원본, 컨설팅 원본, 궁합 원본의 모든 행 수와 SAJU 접근 관계 전체 행 수를 각각 제공한다. 사용자별 SAJU는 접근 행 수, 컨설팅은 접근 관계로 연결되는 서로 다른 컨설팅 ID 수, 궁합은 원래 사용자 ID별 행 수다. 탈퇴 계정 조인으로 행을 누락하지 않는다. 미연결 원본과 공유로 인한 합계 차이도 별도 설명한다. 상세 정의는 명세에 고정한다.

**근거**: 공유 SAJU의 원본 수는 사용자 접근 수와 다르다. 공유 컨설팅의 사용자별 수를 실제 개인 요청 횟수로 해석하면 안 된다. 완료 상태·기간 필터를 넣으면 전체 초기화 대상과 보고 기준이 어긋난다.

**검토한 대안**: 새 피드백 형태로 변환, soft delete 필터, 사용자 개인정보 마스킹, 완료 행만 보고, 접근 수로 원본 수 대체는 모두 사용자의 원본/전체 제공 요구와 맞지 않는다. 원본·집계 자료는 개인정보를 포함하므로 로컬에만 보관한다.

## 8. 전환·검증·복구

**결정**: 분석 쓰기 중단 → 피드백 원본·건수 추출 → 추출 건수와 DB 건수 대조 → 운영자 확인 → 초기화 → 새 스키마 적용 → 배포 순서다. 추출 시작부터 새 스키마 DDL 적용·validate 통과·호환 애플리케이션 배포 완료까지 구형 애플리케이션 전체 중지 또는 사용자·관리자의 읽기·쓰기 트래픽 전체 차단을 유지하고 진행 중 조회·쓰기를 모두 종료한다. 쓰기 경로만 차단하는 방식은 허용하지 않는다. 호환 앱 배포·validate 후에는 일반 트래픽과 구형 앱을 계속 차단하고 호환 앱의 읽기 smoke·테스트 계정의 제한된 쓰기 smoke만 허용하며, 필수 검증 성공 후 일반 트래픽을 재개한다. DDL 적용 직전부터 배포·스키마 검증 완료까지 AnalysisHistoryRepository와 관리자 조회를 포함한 구형 테이블 접근이 실행되지 않음을 확인하며, 조회·쓰기 차단을 보장할 수 없으면 초기화를 중단한다. 차단 방법은 운영자가 선택하며 별도 차단 기능 개발은 범위에 포함하지 않는다. 예정된 차단 해제 전 일반 트래픽 차단이 풀리거나 허용된 smoke 외 쓰기가 발생하면 즉시 전환을 중단한다. 파괴적 초기화·DDL 시작 전이면 차단을 복구한 뒤 원본·건수를 재추출·대조하고 운영자 재확인을 받는다. 파괴적 초기화·DDL을 시작한 이후에는 쓰기를 중지하고 구형 앱의 조회 차단도 유지한 채 실제 DB 상태·적용된 문장과 검증된 백업·복구 자료를 확인한다. 신규 기록 손실을 검토하고 운영자 확인 후 복구·재검증하며, 초기화 전 절차처럼 자료를 단순 재추출하거나 자동 재삭제하지 않는다. 검증 전 백업 덮어쓰기를 금지한다. 원본 제공·대조 또는 운영자 확인이 없으면 삭제를 진행하지 않는다.

보고서 양식과 내보내기·건수 조회·대조·초기화 SQL은 Git에서 제외된 로컬 문서(`specs/007-unify-saju-analysis/local/reset-runbook.md`)로 제공하며 저장소에는 포함하지 않는다. 커밋 대상 설계 문서에는 실제 SQL을 적지 않는다. 전용 실행 패키지·자동 초기화·부팅 시 전환 상태 검사·공개 전환 API는 만들지 않는다. 운영자가 직접 실행하고 복제 DB에서 절차를 먼저 점검한다.

**근거**: 삭제 전 정보 제공과 운영자 확인이 필수다. 피드백·분석 건수 파일은 DB 전체 백업이 아니므로 그것만으로 모든 분석을 복구할 수 있다고 간주하지 않는다. 운영자 확인 전에 대상 DB 전체 백업을 로컬에 확보하고 복구 가능성을 검증하며, 복제 DB에서 해당 백업의 복구 리허설을 완료하고 결과를 로컬에 기록해야 한다. 백업·복구 검증·리허설 결과 중 하나라도 없거나 실패하면 초기화를 중단한다. 초기화 이후 전환 오류가 나면 쓰기를 중지하고 새 데이터 손실 없이 복구할 방법을 확인한 뒤 진행한다. 실패가 있었다는 이유로 확인 없이 다시 삭제하지 않는다.

런타임 JSON·FK·쿼터·동시성·권한·숫자 ID 계약은 자동 테스트한다. 실제 운영 초기화 전용 자동 테스트/runner는 만들지 않는다. 삭제 대상 0건·계정/인증 손실 0건·새 구조 빈 상태를 수동 대조하고 배포 후 새 요청을 검증한다.

## 9. 폐기된 설계 결정 기록 — 현재 구현 지시가 아님

아래는 기존 결정을 삭제하지 않고 남긴 기록이다. 모두 **초기화 결정으로 폐기**됐으며 새 구조로 과거 데이터를 옮기는 절차를 수행하지 않는다.

- **초기화 결정으로 폐기 — 프로필·과거 분석의 계속 유지**: 이전에는 기존 프로필을 남기고 공유 결과를 접근 사용자별 사본으로 연결하기로 했다. 전체 분석·프로필 삭제가 확정돼 과거 사본·소유권 변환이 필요하지 않다.
- **초기화 결정으로 폐기 — 만세력만 제외한 부분 보존**: 이전에는 만세력만 새로 만들고 모든 유형의 과거 결과에 빈 기초 참조와 부재 표시를 두기로 했다. 지금은 모든 결과가 신규 요청에서 생성되므로 모든 유형의 만세력 참조가 필수이며 해당 예외가 사라진다.
- **초기화 결정으로 폐기 — 과거 회사 입력 예외·요약 생성**: 기존 DB에 없는 회사 날짜는 누락 표시로, 없는 컨설팅 요약은 저장 자료와 원본 연도로 재구성하기로 했다. 과거 결과를 제공하지 않으므로 변환·파생 기록이 필요하지 않다.
- **초기화 결정으로 폐기 — 과거 ID 호환·번호 범위 분리**: 이전에는 과거 최대 번호보다 큰 통합 ID와 사용자별 참조 테이블·전환 메타데이터를 두고 링크를 해석하기로 했다. 전체 초기화 후 숫자 ID를 처음부터 발급하므로 과거 ID 저장소·최댓값 조회·번호 경계·resolver·부팅 검증을 없앤다.
- **초기화 결정으로 폐기 — 작성자 사본으로 피드백 재연결**: 기존 피드백을 새 소유자별 결과에 연결하고 구형 FK를 잠시 유지하기로 했다. 지금은 원본 전체를 로컬에 제공한 뒤 삭제하고 새 피드백에는 saju_id 하나만 둔다.
- **초기화 결정으로 폐기 — 소유자 불명·완료 상태에 따른 보존 전환 중단**: 이전에는 불완전 원본을 새 구조에 옮길 수 없어 전환을 중단하기로 했다. 지금은 상태·접근 여부와 무관하게 원본 제공/건수에 포함하고 삭제하며, 새 중단 조건은 자료 누락·대조 불일치·운영자 미확인이다.
- **초기화 결정으로 폐기 — 접근 시각을 사본 시각으로 저장**: 이전에는 과거 SAJU 접근 시각을 사본의 created_at으로, 원본 시각을 별도 참조로 남기기로 했다. 과거 사본 자체가 없어져 신규 결과의 생성 시각만 필요하다.
- **초기화 결정으로 폐기 — 과거 원본/신규 성공 요청 통계 분리**: 이전에는 사본 수 증가를 제거한 과거 원본 집계와 신규 집계를 나누기로 했다. 삭제 전 원본/접근 수를 로컬로 제공한 후 앱에서는 새 saju 행만 단일 집계한다.
- **초기화 결정으로 폐기 — 일회성 SQL로 과거 자료 채우기**: 이전에는 과거 결과·참조·피드백 연결을 같은 데이터 트랜잭션으로 채우고 원본을 계속 남기기로 했다. 지금은 사전 추출·대조·운영자 확인 뒤 전체 초기화한다. 당시 SQL을 대화로만 전달하던 제공 방식도 현재는 폐기한다. 현재 보고서 양식과 SQL은 Git에서 제외된 로컬 실행 문서에 둔다.
- **초기화 결정으로 폐기 — 관리자 과거 기둥 문자열 보존 여부 미결**: 과거 상세를 계속 제공할 때 남았던 질문이다. 전체 초기화로 과거 분석·기둥 표시도 사라지며 현재 사전 제공 범위 밖이다.

## 10. 피드백 개수와 로컬 제공 방식

분석과 피드백의 관계는 1 : 0..1이다. 유형은 연결된 saju.analysis_type으로 알 수 있으므로 feedback_type 컬럼과 feedbackType 요청 필드를 제거한다. 중복 유형 저장으로 불일치가 생기지 않게 하며 관운 대상 피드백은 HTTP 404로 거부하고 관리자 표시·필터도 연결된 분석 유형을 사용한다. 새 피드백의 saju_id에 UNIQUE를 두고 같은 분석의 중복 제출은 409로 거부한다. 초기화 전 원본 제공에는 이 제약을 소급 적용하지 않아 과거 중복 행도 그대로 포함한다.

보고서 양식과 SQL은 Git에서 제외된 로컬 문서(`specs/007-unify-saju-analysis/local/reset-runbook.md`)로 제공하며 저장소에는 포함하지 않는다. 로컬 파일이 없는 clone도 spec.md의 원본 범위·건수 정의와 quickstart.md의 순서·대조 기준을 이해할 수 있어야 한다. 제외 규칙은 .git/info/exclude에만 두고 .gitignore는 바꾸지 않는다.

## 12. 검토 반영 — 물리 스키마와 관리자 기능

**결정**: 행 초기화 후 구형 전용 6개 테이블(user_saju_access, career_consultation, career_fortune, saju_full_data, company_compatibility, saju_result)은 DROP한다. 빈 user_profile·daily_api_usage는 재사용하고 피드백은 구형 대상 FK·두 컬럼·feedback_type을 제거한 뒤 새 관계로 변경한다. CREATE·ALTER·DROP은 구현 담당자가 제외된 로컬 reset-runbook.md f절에 작성·최종 엔티티와 동기화하고 운영자가 실제 DB 대조·리허설·실행을 맡는다.

**근거**: 운영 ddl-auto 기본값은 validate이고 로컬은 update다. 행을 비우거나 엔티티 필드를 제거하는 것만으로 구형 물리 컬럼과 NOT NULL 제약의 정리가 보장되지 않는다. 운영과 로컬 모두 명시적 전환 DDL을 적용하고 validate 및 물리 스키마 대조를 수행한다. DDL은 암묵적 커밋을 수반하므로 e절 행 삭제와 분리한다.

**관리자 변경 범위**: AdminUserQueryRepository의 구형 native SQL·회원 분석 건수 및 이를 사용하는 AdminUsageAdjustmentService, AdminDashboardService의 당일 분석·피드백 요약, AdminFeedbackQueryRepository의 목록/count/상세/만족도별 통계, 관련 서비스·DTO·Thymeleaf 화면을 모두 포함한다. 회원 건수는 saju.user_id별 결과 수, 분석 통계는 saju.analysis_type·created_at, 피드백 유형은 saju_id 조인의 saju.analysis_type을 기준으로 한다. 기존 관리자 응답의 feedbackType·유형별 통계 필드명과 type 필터·SAJU 거부 예외는 유지하고 작성 요청 필드 제거와 구분한다.

**새 피드백 작성자**: user_id는 NOT NULL이며 인증 사용자와 결과 소유자가 같아야 한다. 기존 탈퇴 시 피드백 삭제를 유지하므로 실제 DB에 탈퇴 사용자 피드백이 0건이어도 정상이다. 전환 원본은 존재하는 모든 행·컬럼을 그대로 제공하고 새 제약으로 거르거나 이미 삭제된 행을 복원하지 않는다.

## 13. 분석의 중복 프로필 FK 제거

**결정**: saju의 프로필 FK를 제거하고 실제 분석 프로필을 saju.manse_id → manse.user_profile_id로 조회한다. users.user_profile_id는 사용자 기본값으로 유지한다.

**근거**: 모든 분석은 만세력을 필수 참조하고 만세력의 프로필은 하나다. 별도 FK의 조회 성능상 이점은 입증되지 않았으며 중복 저장과 일치 검증 부담을 없애는 편이 단순하다. 요청 입력과 해당 만세력 프로필을 선택하는 업무 검증은 유지하되 두 개의 프로필 FK를 비교하는 검증은 제거한다. 만세력의 프로필 참조를 생성 후 바꾸지 않아 기본값 변경이 과거 분석의 프로필을 바꾸지 않게 한다.

## 14. 전환 후 회원 탈퇴 정책

**결정**: 기존처럼 계정 soft delete로 이름·이메일을 대체하고 피드백만 hard delete한다. 새 기본 프로필 참조는 NULL로 해제하되 saju와 소유자 FK·만세력 참조·스냅샷, 공유 프로필·만세력은 유지한다. 관리자 건수·권한 있는 상세에는 탈퇴 사용자 분석도 포함한다. 일일 사용량·인증 세션 무효화는 기존 탈퇴 동작을 유지한다.

**근거**: 사용자가 분석 기록을 남기는 기존 정책 유지를 선택했다. 계정 정보의 표시 제한과 분석 보존을 구분한다. 내부 소유자 연결·출생정보·결과 스냅샷이 남으므로 완전한 익명화가 아니다. 공유 자료는 다른 사용자가 참조하므로 탈퇴에 따라 삭제하지 않는다. 피드백 삭제·기본 참조 해제·soft delete는 원자적으로 처리하고 사용자 행의 짧은 잠금·활성 확인으로 최종 쓰기와 순서를 정한다. 외부 API 동안 잠금을 잡지 않는다.

## 15. 스키마 전환의 공식 자료

MySQL의 CREATE·ALTER·DROP은 [MySQL 8.0 암묵적 커밋 규칙](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html)을 따른다. 행 삭제와 DDL을 분리하고 전체 트랜잭션 롤백을 보장하지 않는 이유다. Hibernate의 validate는 스키마를 변경하지 않고 update는 부족한 구조 추가·형식 변경을 수행하므로, 구형 물리 구조 제거를 포함한 전환은 명시적 DDL과 별도 스키마 대조로 수행한다. [Hibernate 스키마 관리 안내](https://docs.hibernate.org/orm/7.2/introduction/html_single/)를 근거로 한다.
