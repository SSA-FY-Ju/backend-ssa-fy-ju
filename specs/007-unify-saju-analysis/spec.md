# 기능 명세: 분석 결과 통합 및 요청별 독립 저장

**기능 브랜치**: `007-unify-saju-analysis`

**작성일**: 2026-10-19 | **수정일**: 2026-10-31

**상태**: 명세·설계·작업 목록 작성 및 검토 피드백 반영 완료. 구현·실제 내보내기·초기화는 미수행이다.

**입력**: 관운·커리어 컨설팅·회사 궁합 결과를 `saju`로 통합하고 요청마다 독립 저장한다. 계정과 인증 데이터는 유지하고 기존 분석·피드백·프로필·사용량은 초기화한다. 초기화 전에 피드백 원본 전체와 분석 건수를 로컬로 제공하고 운영자 확인을 받는다. 결제·백엔드 재전송 중복 방지는 범위 밖이다.

## 확정 사항

- 이번 전체 초기화 결정은 이전 보존 이관 및 만세력만 이관에서 제외하던 결정을 대체한다. 폐기된 설계의 이유는 [research.md](research.md)에 기록한다.
- 다음 테이블의 모든 행을 초기화한다: `saju_result`, `saju_full_data`, `career_fortune`, `user_saju_access`, `career_consultation`, `company_compatibility`, `user_satisfaction_feedback`, `user_profile`, `daily_api_usage`.
- `users`와 인증 관련 데이터는 유지한다. 계정·탈퇴 상태·인증 정보를 지우거나 초기화하지 않는다.
- 새 `user_profile`, `manse`, `saju`, 피드백은 빈 상태에서 시작한다. 일일 사용량도 비워지므로 전환 당일 이미 소모한 쿼터가 재설정된다. 전환 후 컨설팅·궁합 하루 공유 3회 정책과 실패 보상 정책은 유지한다.
- 운영자 확인 전에는 초기화하지 않는다. 전환 순서는 분석 쓰기 중단 → 피드백 원본·건수 추출 → 추출 건수와 DB 건수 대조 → 운영자 확인 → 초기화 → 새 스키마 적용 → 배포다.
- 건수 보고서 양식과 내보내기·건수 조회·대조·초기화 SQL은 Git에서 제외된 로컬 문서(`specs/007-unify-saju-analysis/local/reset-runbook.md`)로 제공하며 저장소에는 포함하지 않는다. 커밋 대상 설계 문서에는 실제 SQL을 적지 않는다. 개인정보가 포함된 원본 및 집계 결과물은 로컬에만 보관한다.

## 사용자 시나리오 및 검증

### 사용자 시나리오 1 - 같은 입력으로 새 분석 받기 (우선순위: P1)

인증된 사용자는 세 유형 중 원하는 분석을 요청한다. 같은 달에 같은 입력으로 다시 요청해도 새로 분석한 결과와 이전 결과를 구별하는 기록을 갖는다. 생년월일·출생 시각이 같으면 프로필과 만세력은 재사용한다.

**우선순위 근거**: 요청별 결과 보관이 핵심이며, 결과 재사용·덮어쓰기를 없애야 이력 관리가 정확해진다.

**독립 검증**: 쿼터 등 허용 조건을 충족한 사용자로 세 유형 각각 같은 입력 요청을 3번 성공시키고, 서로 다른 분석 ID 3개와 재사용된 프로필·만세력 참조를 확인한다.

**인수 시나리오**:

1. **조건** 유효한 입력과 분석 가능한 사용자, **실행** 같은 생년월일·출생 시각으로 관운을 3번 성공적으로 요청, **결과** 프로필 1개·만세력 1개를 재사용하며 사용자 소유의 결과 3건이 각각 다른 ID로 저장된다.
2. **조건** 같은 사용자·회사·설립일시·직무·월의 궁합 결과, **실행** 같은 입력으로 새 궁합 분석 완료, **결과** 기존 결과를 수정하거나 반환하지 않고 새 분석 결과를 새 ID로 저장·반환한다.
3. **조건** 같은 사용자·프로필·월의 컨설팅 결과, **실행** 같은 입력으로 새 컨설팅 완료, **결과** 기존 결과·모델 버전과 관계없이 새로 분석·저장한다.
4. **조건** 같은 입력의 요청 2개가 동시에 도착하고 각각 허용 조건을 충족, **실행** 둘 다 분석·저장에 성공, **결과** 각 요청은 자기 결과와 별도 ID를 받는다. 프로필·만세력은 중복 생성되지 않고 두 결과가 하나로 합쳐지지 않는다.

### 사용자 시나리오 2 - 자신의 분석 이력을 안전하게 조회하기 (우선순위: P1)

사용자는 마이페이지에서 기간 제한 없이 세 유형의 전체 개별 이력을 페이지로 조회하고 선택한 결과의 상세 내용을 확인한다. 같은 출생 정보를 가진 다른 사용자와 기초 정보를 공유해도 결과는 요청 사용자만 소유한다.

**우선순위 근거**: 공유 기초 정보와 개인 결과를 구분해야 개인정보와 이력의 정확성을 보장한다.

**독립 검증**: 같은 프로필을 사용하는 두 사용자의 결과를 만들고 각자의 목록·상세 접근 범위를 검증한다.

**인수 시나리오**:

1. **조건** 같은 생년월일·출생 시각으로 요청하는 A와 B, **실행** 각자의 분석 성공, **결과** 프로필·만세력은 공유하지만 분석 ID와 소유권은 분리된다.
2. **조건** 같은 입력으로 생성한 결과 3건, **실행** 소유자가 마이페이지 조회, **결과** 유형·생성 시각·ID로 각 기록을 구별하고 각각의 상세 화면을 열 수 있다.
3. **조건** 저장된 결과와 소유자, **실행** 그 결과를 두 번 상세 조회, **결과** 같은 저장 내용과 ID를 반환하고 분석 실행·새 결과 생성·분석 쿼터 차감이 발생하지 않는다.
4. **조건** 타인 소유의 결과 ID를 알거나 같은 프로필을 참조하는 일반 사용자, **실행** 해당 결과 조회·피드백 시도, **결과** HTTP 404로 거부되고 결과 내용이 노출되지 않는다.
5. **조건** 인증되지 않은 요청, **실행** 새 분석·개인 이력·상세 조회 시도, **결과** 인증 실패로 거부되고 새 분석이 실행되거나 저장되지 않는다.

### 사용자 시나리오 3 - 유형에 맞는 분석과 검증 받기 (우선순위: P1)

사용자는 선택한 유형에 필요한 정보를 입력하고 해당 유형의 결과를 받는다. 통합 저장 후에도 필수 입력과 분석 결과 검증이 유지된다.

**우선순위 근거**: 유형별 의미와 검증을 유지해야 잘못된 입력이나 불완전한 결과가 정상 기록으로 남지 않는다.

**독립 검증**: 세 유형별 정상 입력, 필수 항목 누락, 잘못된 값, 유효하지 않은 외부 분석 응답을 각각 검사한다.

**인수 시나리오**:

1. **조건** 세 유형 각각의 유효한 입력, **실행** 분석 성공, **결과** 요청 유형의 결과와 해당 요청 ID를 반환하고 저장 후 조회해도 입력·결과의 값과 의미가 보존된다.
2. **조건** 회사 궁합의 필수 회사 정보 등 유형별 입력 누락·잘못된 값, **실행** 요청 제출, **결과** 기존 유형별 검증 기준에 따라 거부되고 정상 결과가 생성되지 않는다.
3. **조건** 지원하지 않는 유형 또는 필수 값·허용 범위 등 기존 검증 기준을 위반하는 외부 응답, **실행** 처리 시도, **결과** 정상 분석으로 저장·반환하지 않고 실패로 처리한다.
4. **조건** 유효한 프로필·만세력이 이미 존재, **실행** 다른 유형으로 요청, **결과** 기초 정보는 재사용하고 해당 유형의 분석은 새로 수행한다. 컨설팅·궁합 요청만으로 별도의 관운 분석 이력을 자동 생성하지 않는다.

### 사용자 시나리오 4 - 관리자 조회와 피드백의 대상 유지하기 (우선순위: P2)

관리자는 세 유형의 분석 기록을 사용자·유형·생성 시각과 함께 조회한다. 피드백은 여러 번 수행한 분석 중 정확히 하나를 가리킨다.

**우선순위 근거**: 통합 이후에도 운영 조회와 피드백이 올바른 요청 건을 가리켜야 고객 대응이 가능하다.

**독립 검증**: 같은 입력의 컨설팅·궁합 결과 각각에 피드백을 연결하고 관리자 목록·상세·피드백 연결을 확인한다.

**인수 시나리오**:

1. **조건** 세 유형의 반복 분석 기록, **실행** 관리자가 목록·상세와 기존 검색·필터·페이지 조회 사용, **결과** 각 결과의 소유자·유형·ID·생성 시각·내용이 일치하고 반복 요청도 각각 집계된다.
2. **조건** 같은 사용자의 같은 입력 컨설팅 또는 궁합 2건, **실행** 하나에 피드백 제출, **결과** 선택한 분석 ID에만 연결된다.
3. **조건** 피드백 대상이 관운 분석인 요청, **실행** 저장 시도, **결과** 연결된 saju.analysis_type으로 관운을 확인해 HTTP 404로 거부한다. 클라이언트가 피드백 유형을 별도로 전달하지 않는다.
4. **조건** 관리자 권한이 없는 사용자, **실행** 관리자 분석·피드백 조회 시도, **결과** 기존 관리자 접근 정책에 따라 거부된다.

### 사용자 시나리오 5 - 초기화 전에 원본과 건수를 확인하기 (우선순위: P1)

운영자는 삭제 전에 피드백 원본 전체와 분석 건수를 로컬로 제공받고 DB와 대조한 뒤 초기화 여부를 확인한다. 기존 사용자의 마이페이지 이력과 피드백이 사라지고 당일 사용량이 재설정되는 영향을 알고 확인한다.

**독립 검증**: 테스트용 전환 자료에는 탈퇴 사용자 피드백·공유 SAJU·사용자별 컨설팅 접근·궁합을 포함해 제공 범위와 대조 기준을 확인한다. 실제 운영 DB에서 탈퇴 사용자 피드백이 0건이어도 정상이다. 기존 탈퇴 처리로 이미 삭제된 행은 복원하지 않고 추출 시점에 존재하는 모든 행을 대상으로 한다. 운영자 확인이 없는 상태에서는 초기화 단계로 진행하지 않는다.

**인수 시나리오**:

1. **조건** 탈퇴 사용자의 행을 포함한 피드백 테이블, **실행** 초기화 전 원본 제공, **결과** 모든 행·모든 컬럼이 원본 값 그대로 로컬에 제공되고 조인·가공·마스킹·필터가 없다.
2. **조건** 공유 분석 원본과 접근 관계, **실행** 건수 제공, **결과** 세 유형 총 건수, 별도의 SAJU 접근 건수, 사용자별·유형별 건수와 각 산정 기준을 함께 제공한다.
3. **조건** 추출 자료, **실행** DB 대조, **결과** 피드백 행 수·컬럼·값과 각 건수 지표가 같은 정지 시점의 DB와 일치해야 한다. 공유 구조 때문에 사용자별 합계와 원본 합계가 다를 수 있다는 기준을 명시한다.
4. **조건** 자료 누락·불일치 또는 운영자 미확인, **실행** 전환 진행, **결과** 초기화하지 않는다.
5. **조건** 대조 완료와 운영자 확인, **실행** 초기화·새 스키마 적용·배포, **결과** 분석·피드백·프로필·사용량은 비어 있고 계정과 인증 데이터는 유지된다. 과거 마이페이지 이력은 없으며 새 분석은 숫자 ID를 처음부터 발급한다.

### 사용자 시나리오 6 - 현행 일일 쿼터 안에서 새 분석 받기 (우선순위: P1)

사용자는 기존과 같은 쿼터 적용 범위와 한도를 따른다. 결과 캐시가 제거되므로 과거와 같은 입력이어도 새 컨설팅·궁합 요청은 새 분석으로 사용량에 반영된다.

**우선순위 근거**: 현행 정책을 유지하면서 반복 요청의 비용과 한도 처리가 일관되어야 한다.

**독립 검증**: 컨설팅·궁합 혼합 요청으로 하루 공유 한도를 검증하고, 실패·저장 후 응답 유실·상세 조회 및 관운 요청의 사용량을 확인한다.

**인수 시나리오**:

1. **조건** 오늘 사용량이 0인 사용자, **실행** 컨설팅·궁합을 합쳐 3회 성공 후 네 번째 요청, **결과** 성공 3회가 같은 사용자 일일 한도를 소모하고 네 번째는 쿼터 초과로 새 분석 없이 거부된다. 입력이 같아도 성공 요청마다 1회를 사용한다.
2. **조건** 차감 후 외부 호출·결과 검증·저장 실패, **실행** 기존 보상 경로 실행, **결과** 원래 차감 날짜의 사용량을 복원한다. 자정을 넘겨도 다음 날 사용량을 잘못 복원하지 않으며, 복원 자체가 실패하면 기존 오류 기록·원래 실패 전파 정책을 유지한다.
3. **조건** 저장까지 성공한 결과, **실행** 응답 유실 또는 저장 후 응답 처리 실패, **결과** 이미 완료된 분석의 쿼터를 복원하지 않는다. 재요청은 한도가 허용하면 추가 분석·차감으로 처리한다.
4. **조건** 관운 요청 또는 저장된 상세 결과 조회, **실행** 처리 완료, **결과** 관운에는 이번 통합으로 쿼터를 새로 적용하지 않고, 상세 조회는 쿼터를 소모하지 않는다.
5. **조건** 쿼터 잔여량이 1인 사용자에게 컨설팅·궁합 요청 2개가 동시 도착, **실행** 요청 허용 여부 판정, **결과** 최대 1개만 허용되고 다른 요청은 한도 초과로 거부되어 하루 공유 한도를 넘지 않는다.

### 사용자 시나리오 7 - 기본 출생정보 또는 다른 출생정보로 분석하기 (우선순위: P1)

사용자는 기본 출생정보를 저장하고 분석 전에 기본 프로필을 사용할지 다른 출생정보를 입력할지 선택할 수 있다. 선택 화면의 프론트 구현은 범위 밖이며 기본값 조회·저장과 분석 입력의 백엔드 계약을 정의한다.

**우선순위 근거**: 기본 출생정보 선택과 실제 분석 입력을 분리해 공유 프로필·기존 결과를 바꾸지 않고 분석할 수 있어야 한다.

**독립 검증**: 기본값 미설정·저장·조회·변경과 기본값/다른 입력 분석을 검증한다. 기본값 저장의 외부 호출·만세력 생성·분석·차감은 0이며 공유 프로필·과거 결과·진행 중 입력은 유지된다.

**인수 시나리오**:

1. **조건** 기본 프로필이 없는 사용자, **실행** 기본값 조회, **결과** 미설정임을 반환하고 직접 입력을 안내할 수 있다. 기본 출생정보 저장만으로 만세력·분석·쿼터 사용은 생기지 않는다.
2. **조건** 기본 프로필이 있는 사용자, **실행** 기본값을 선택하여 분석 요청, **결과** 선택한 출생정보로 분석하고 결과는 인증 사용자가 소유한다.
3. **조건** 기본 프로필이 있는 사용자, **실행** 다른 출생정보로 분석, **결과** 해당 입력의 프로필로 결과를 저장하며 기본 프로필은 바꾸지 않는다.
4. **조건** 과거 결과와 공유 프로필, **실행** 기본 출생정보 변경, **결과** 사용자 기본 참조만 교체하고 다른 사용자·과거 결과·진행 중 요청에서 확정한 입력은 바꾸지 않는다.

### 예외 및 실패 처리

- 같은 입력의 동시 요청은 각각 분석·저장하고 프로필·만세력만 중복 생성되지 않게 한다.
- 외부 호출·검증·저장 실패는 정상 결과로 저장하거나 과거 결과로 대체하지 않는다.
- 저장 후 응답 유실은 별도 재요청을 유발할 수 있다. 한도 내에서 각 성공 요청이 별도 결과와 비용·사용량을 만든다.
- 조회·피드백의 없는 ID·타인 ID는 결과를 노출하지 않고 거부한다. 상세의 요청 유형 불일치도 404로 거부하고 피드백 허용 유형은 연결된 saju.analysis_type으로 검증하며 관운 대상은 404로 거부한다.
- 초기화 전 결과는 삭제하고 신규 결과만 조회한다. 분석 ID는 BIGINT 자동 증가로 새로 발급하며 과거 최댓값·번호 경계·ID 매핑을 사용하지 않는다. 예전 URL의 영구 404는 보장하지 않는다.
- 초기화 전 피드백 원본 제공은 정상·비정상·사용자 연결 여부와 관계없이 테이블 전체를 대상으로 한다. 탈퇴 사용자 행이나 작성자 없는 행을 제외하지 않는다.
- 추출 중 관련 데이터가 바뀌지 않도록 분석·피드백·프로필·사용량 및 해당 데이터를 바꾸는 회원 탈퇴 처리를 중지하고 진행 중 쓰기를 종료시킨다.
- 추출·대조 실패나 운영자 미확인 시 데이터를 삭제하지 않는다. 이번 문서 수정 요청은 향후 실행 단계의 운영자 확인을 대신하지 않는다.

## 요구사항

### 기능 요구사항

- **FR-001**: 세 유형의 결과를 `saju`로 통합하고 유형을 식별해야 한다.
- **FR-002**: 성공 요청마다 새 ID·생성 시각의 독립 결과 한 건을 저장해야 한다. 입력·월·회사·직무·모델이 같아도 재사용·갱신하지 않는다.
- **FR-003**: 프로필과 만세력은 결과와 분리해 같은 출생정보에 재사용한다. 프로필은 기본 출생정보 저장 또는 신규 분석 요청에서 생성하며, 만세력은 신규 분석 요청에서 해당 프로필에 없을 때 FastAPI 결과로 최초 생성한다. 동시 생성에도 중복되지 않아야 한다.
- **FR-004**: 결과는 인증된 요청 사용자 한 명에게 직접 귀속된다. 기초 정보 공유로 타인 결과 접근 권한이 생기지 않는다.
- **FR-005**: 결과의 ID·소유자·유형·만세력 참조·생성 시각·유형별 입력과 결과를 저장한다. 실제 분석 프로필은 saju → manse → user_profile로 조회하고 saju에 프로필 FK를 중복 저장하지 않는다. 모든 유형의 `manse_id`는 NOT NULL이다. `saju`의 시각 컬럼은 `created_at` 하나다.
- **FR-006**: 기존 유형별 요청·외부 응답·내부 계산 결과 검증의 의미를 유지한다.
- **FR-007**: 기존 AnalysisType 세 전략은 유형별 분석·검증을, 공통 서비스는 인증·쿼터·소유권·저장을 담당한다.
- **FR-008**: 결과 캐시·덮어쓰기·저장 경합 승자 반환·요청 합치기·결과 유일 제약을 제거하고 기초 정보 중복 방지는 유지한다.
- **FR-009**: 상세 조회는 저장된 결과 스냅샷만 반환하며 분석 실행·새 결과·쿼터 차감이 없어야 한다.
- **FR-010**: 마이페이지는 기간 제한 없이 소유자의 전체 개별 성공 요청을 created_at DESC,id DESC 순서로 페이지 조회한다. 목록과 count는 같은 소유자·유형 조건을 사용한다. 초기화 후 과거 분석 이력은 없고 새 요청부터 기록한다.
- **FR-011**: 관리자 권한과 기존 검색·기간·유형·페이지 기능을 유지한다. 통계는 전환 후 `saju` 한 행을 성공 분석 한 건으로 단일 집계하며 과거 별도 집계는 하지 않는다.
- **FR-012**: 피드백은 `saju_id` FK 하나로 특정 결과를 참조하며 작성자 user_id를 NOT NULL로 두고 인증 사용자·결과 소유자와 같음을 검증한다. 허용 유형은 연결된 saju.analysis_type으로 검증한다. 피드백 테이블에 feedback_type을 저장하거나 요청 DTO에 feedbackType을 받지 않는다. 분석 한 건당 피드백은 0개 또는 1개로 제한하고 saju_id에 UNIQUE를 둔다. 같은 분석의 중복 제출은 409로 거부한다. 컨설팅·궁합만 허용하고 관운·타인·없는 분석 대상은 HTTP 404로 거부한다.
- **FR-013**: 생성·목록·상세·관리자·피드백의 분석 ID는 같은 `saju` 기록을 가리킨다. 분석 ID는 기존 숫자 형식을 유지하고 새 테이블의 BIGINT 자동 증가로 처음부터 발급한다. 과거 최댓값 조회·시작 번호 보정·ID 호환 매핑·예전 URL의 영구 404 보장은 제공하지 않는다.
- **FR-014**: 검증된 성공 결과만 원자적으로 저장한다. 실패 시 해당 결과를 롤백하며 진행 중·실패 결과 행과 completed 컬럼은 두지 않는다.
- **FR-015**: 반복·동시 요청, 기초 재사용, 검증, 소유권, ID, 개인·관리자 조회, 피드백, 쿼터, 실패 경계를 검증하는 런타임 테스트를 포함한다.
- **FR-016**: 결제·order_item_id·백엔드 요청 중복 방지·프론트 구현은 범위 밖이다.
- **FR-017**: 초기화 전에 운영자에게 `user_satisfaction_feedback`의 모든 행·모든 컬럼을 원본 그대로 제공해야 한다. 조인·가공·마스킹·필터 없이 탈퇴 사용자 행도 포함한다. 개인정보가 포함된 결과물은 로컬에만 보관한다. 추출 자료의 행 수·컬럼·값이 같은 시점의 DB 원본과 일치해야 한다.
- **FR-018**: 전환 후 컨설팅·궁합은 사용자별 하루 합산 3회, 관운은 미적용이다. 같은 입력도 1회 차감하고 동시 한도를 넘지 않는다. 차감 후 외부·검증·저장 실패는 원래 날짜로 복원하고 복원 실패 기록·원래 오류 전파를 유지한다. 저장 성공 후 응답 실패는 복원하지 않으며 상세 조회는 차감하지 않는다. 전환 때 daily_api_usage를 비우므로 당일 기존 사용량도 재설정된다. 관운의 동일 입력도 성공 요청마다 saju 결과를 새로 저장하고 user_profile·manse만 재사용한다. 결과 누적은 의도한 정책이며 추가 한도는 이번 범위에 넣지 않는다.
- **FR-019**: 초기화 전에 유형별 총 건수, 별도 SAJU 사용자 접근 건수, 사용자별·유형별 건수 및 각 산정 기준을 운영자에게 제공해야 한다. 건수 정의는 아래 표를 따른다. 같은 정지 시점의 DB와 대조하고, 원본 제공·건수 대조·운영자 확인이 모두 완료되기 전에는 초기화하지 않는다.
- **FR-020**: 분석 쓰기 중단 → 피드백 원본·건수 추출 → 추출 건수와 DB 건수 대조 → 운영자 확인 → 초기화 → 새 스키마 적용 → 배포 순서를 지켜야 한다. 확정된 삭제 대상 모든 행만 초기화하고 users와 인증 데이터는 유지한다. 새 분석 구조는 빈 상태에서 시작한다.
- **FR-021**: 건수 보고서 양식과 내보내기·건수 조회·대조·초기화 SQL은 Git에서 제외된 로컬 문서(`specs/007-unify-saju-analysis/local/reset-runbook.md`)로 제공하며 저장소에는 포함하지 않는다. 항목 정의는 이 명세에 유지하고 실제 SQL은 커밋 대상 문서에 넣지 않는다. 애플리케이션에 전환 전용 실행 패키지·자동 초기화·전용 API를 추가하지 않는다. 원본과 집계 결과물도 Git이나 원격 서비스에 올리지 않고 로컬에만 보관한다.

- **FR-022**: 사용자는 기본 출생정보를 조회·명시적으로 저장·변경할 수 있어야 한다. `users.user_profile_id`는 NULL 허용 FK이며 같은 프로필을 여러 사용자가 참조할 수 있다. 미설정이면 직접 입력을 안내할 수 있어야 한다. 기본 출생정보 저장은 만세력 생성·분석 실행·쿼터 차감을 유발하지 않는다.
- **FR-023**: 분석은 기본값 선택 또는 다른 출생정보 입력으로 확정한 요청값을 사용한다. 실제 분석 프로필은 `saju.manse_id → manse.user_profile_id`로 참조하고 `saju.user_id`는 인증된 요청 사용자다. 분석 요청으로 기본 프로필을 자동 변경하지 않는다. 공유 프로필의 출생정보는 변경하지 않으며 기본값 변경은 참조 교체로 처리해 과거 결과와 진행 중 요청의 입력을 유지한다.

- **FR-024**: 행 초기화 후 새 스키마 적용 단계에서 구형 전용 6개 테이블(user_saju_access, career_consultation, career_fortune, saju_full_data, company_compatibility, saju_result)을 DROP한다. 빈 user_profile·daily_api_usage는 재사용하고 피드백은 구형 대상 FK·컬럼과 feedback_type을 제거해 새 구조로 변경한다. 새 manse·saju와 사용자 기본 참조·제약·인덱스를 명시적인 DDL로 적용한다. DDL 작성·동기화는 구현 담당자, 실제 스키마 대조·리허설·실행은 운영자가 맡는다. 실제 DDL은 Git에서 제외된 로컬 reset-runbook.md의 f절에만 둔다. 운영·로컬 모두 동일한 전환 DDL과 검증을 사용하며 ddl-auto의 자동 변경에 전환을 맡기지 않는다.
- **FR-025**: 관리자 분석 조회뿐 아니라 회원 목록·상세의 분석 건수, 사용량 조정의 회원 확인, 대시보드, 피드백 목록·상세·유형별 통계를 새 구조에 맞춘다. 회원 분석 건수는 saju.user_id, 분석 유형·날짜 집계는 saju.analysis_type·created_at, 피드백 유형은 saju_id로 연결한 saju.analysis_type을 사용한다. 관리자 경로·권한·기존 응답 필드와 필터는 유지하고 구형 테이블·피드백 유형 컬럼 조회를 없앤다.

- **FR-026**: 전환 후 회원 탈퇴는 기존 계정 soft delete·이름/이메일 대체·인증 세션 무효화와 피드백 hard delete를 유지한다. users.user_profile_id는 NULL로 해제하지만 saju의 소유자·만세력 참조·입력/결과 스냅샷, 공유 프로필·만세력은 유지한다. 원래 계정 이름·이메일은 표시하지 않으며 관리자 분석 집계·기존 권한의 상세에는 남은 분석을 포함한다. 출생정보·스냅샷과 내부 소유자 연결은 남으므로 완전한 익명화로 표현하지 않는다. 피드백 삭제·기본 참조 해제·soft delete는 원자적으로 처리하고 탈퇴 완료 뒤 분석 결과·피드백·기본값 저장은 거부한다. 일일 사용량은 기존 탈퇴 정책을 유지한다.

### 초기화 전 건수 산정 기준

모든 지표는 같은 쓰기 중단 시점의 모든 행을 기준으로 하며 완료 상태·기간·사용자 탈퇴 여부로 거르지 않는다. 계정 조인 때문에 존재하는 분석이나 접근 행이 빠져서는 안 된다.

| 제공 지표 | 산정 기준 |
|---|---|
| SAJU 원본 총 건수 | saju_result의 모든 행 수. career_fortune 수로 대체하지 않음 |
| CAREER_CONSULTATION 총 건수 | career_consultation의 모든 행 수 |
| COMPANY_COMPATIBILITY 총 건수 | company_compatibility의 모든 행 수 |
| SAJU 사용자 접근 총 건수 | user_saju_access의 모든 행 수. 원본 분석 수와 별도 제공 |
| 사용자별 SAJU 건수 | user_saju_access를 원래 user_id별로 센 접근 행 수 |
| 사용자별 CAREER_CONSULTATION 건수 | user_saju_access의 saju_result_id로 연결되는 career_consultation 중 사용자별 서로 다른 consultation ID 수. 실제 개인 요청 횟수가 아닌 공유 접근 기준 |
| 사용자별 COMPANY_COMPATIBILITY 건수 | company_compatibility의 원래 user_id별 행 수 |

탈퇴 사용자도 원래 user_id로 포함하고 사용자 연결이 없는 값은 제외하지 않고 별도 미연결 항목으로 보고한다. 각 사용자에 대해 세 유형을 구분하며 해당 유형이 없으면 0으로 표시한다. SAJU 접근 합계는 원본 수와 다를 수 있고, 공유 컨설팅의 사용자별 합계도 원본 총합과 같을 필요가 없다. 대조 자료에 그 이유와 연결되지 않은 원본 수를 함께 적어 차이를 숨기지 않는다.

### 설계 제약과 영향

- 추출 시작부터 새 스키마 DDL 적용·validate 통과·호환 애플리케이션 배포 완료까지 구형 애플리케이션 전체 중지 또는 사용자·관리자의 읽기·쓰기 트래픽 전체 차단을 유지하고 진행 중 조회·쓰기를 모두 종료한다. 쓰기 경로만 차단하는 방식은 허용하지 않는다. DDL 적용 직전부터 배포·스키마 검증 완료까지 AnalysisHistoryRepository와 관리자 조회를 포함한 구형 테이블 접근이 실행되지 않음을 확인하며, 조회·쓰기 차단을 보장할 수 없으면 초기화를 중단한다. 차단 방법은 운영자가 선택하며 별도 차단 기능 개발은 범위에 포함하지 않는다. 차단 해제 전에 호환 앱에만 검증 접근을 허용해 읽기 smoke와 테스트 계정의 제한된 쓰기 smoke를 수행하고 필수 검증이 모두 성공한 뒤 일반 읽기·쓰기 차단을 해제한다. 예정된 차단 해제 전 일반 트래픽 차단이 풀리거나 허용된 smoke 외 쓰기가 발생하면 즉시 전환을 중단한다. 파괴적 초기화·DDL 시작 전이면 차단을 복구한 뒤 원본·건수를 재추출·대조하고 운영자 재확인을 받는다. 파괴적 초기화·DDL을 시작한 이후에는 쓰기를 중지하고 구형 앱의 조회 차단도 유지한 채 실제 DB 상태·적용된 문장과 검증된 백업·복구 자료를 확인한다. 신규 기록 손실을 검토하고 운영자 확인 후 복구·재검증하며, 초기화 전 절차처럼 자료를 단순 재추출하거나 자동 재삭제하지 않는다. 검증 전 백업 덮어쓰기를 금지한다.

- 운영자 확인 전에 대상 DB 전체 백업을 로컬에 확보하고 복구 가능성을 검증하며, 복제 DB에서 해당 백업의 복구 리허설을 완료하고 결과를 로컬에 기록해야 한다. 백업·복구 검증·리허설 결과 중 하나라도 없거나 실패하면 초기화를 중단한다.

- 분석·프로필·사용량 삭제 범위와 계정·인증 유지 범위는 확정 사항이다. 초기화는 미래 운영 절차이며 이번 문서 수정에서 실행하지 않는다.
- `user_profile`, `manse`, `saju`, 피드백은 빈 상태에서 출발한다. 만세력의 기둥·천간/지지 배열·일간/오행·태양 보정·십성/지장간 공통 계산은 data_json 하나에 저장하고 ManseData record로 다룬다. ID·프로필 FK·시각은 일반 컬럼으로 유지하며 기존 필수값·배열 길이·허용값 검증을 유지한다. 최종 해석은 요청별 result_json에 저장한다.
- 과거 데이터용 nullable 참조·누락 입력·파생 기록·ID 매핑·전환 메타데이터·부팅 검사·분리 통계는 새 구조에 두지 않는다.
- 입력·결과는 기존 유형별 DTO와 검증을 유지한다. 외부 호출 중 DB 트랜잭션을 유지하지 않는다.
- 기존 마이페이지 분석 이력·피드백·관리자 과거 분석과 기둥 문자열은 초기화로 사라진다. 과거 기둥 문자열 별도 보존 여부는 더 이상 미결 사항이 아니다. 확정된 사전 제공 범위는 피드백 원본과 분석 건수다.

### 주요 엔티티

- **분석 기록**: 성공 요청 한 건, 숫자 식별자·소유자·유형·필수 만세력 참조(프로필은 만세력 경유)·created_at·입력/결과 스냅샷.
- **프로필**: 생년월일·시각으로 식별하는 재사용 자료. 모든 기존 행을 비우고 기본 출생정보 저장 또는 새 분석 요청에서 생성한다. 공유 출생정보는 변경하지 않는다.
- **만세력**: 프로필당 하나의 FastAPI·공통 계산 결과. 계산 데이터 전체는 data_json 하나로 저장하며 모든 분석 유형이 필수 참조한다.
- **사용자**: 기존 계정·인증 주체를 유지하며 선택적인 기본 프로필 참조를 가진다. 초기화 후 기본 참조는 NULL로 시작한다.
- **피드백**: 새 분석 한 건당 최대 하나의 평가. 대상 FK는 UNIQUE인 saju_id 하나이며 분석 유형은 연결된 saju.analysis_type에서 얻는다.
- **일일 사용량**: 전체 행을 초기화한 뒤 기존 공유 3회 정책으로 새로 기록한다.

## 성공 기준

### 측정 가능한 결과

- **SC-001**: 전환 후 같은 입력의 성공 요청 3회를 유형별로 실행하면 ID 3개·결과 3건이 남고 앞선 신규 결과도 유지된다.
- **SC-002**: 같은 출생정보를 쓰는 두 사용자의 반복 요청에서 프로필·만세력은 각각 한 건이고 결과 소유자는 100% 요청 사용자다.
- **SC-003**: 생성·목록·상세·관리자·피드백 참조가 100% 같은 기록을 가리킨다. 타인 결과 조회·피드백은 404이며 비관리자 접근은 기존 관리자 권한 정책으로 거부한다. 신규 분석은 서로 다른 숫자 ID를 갖고 과거 번호와의 범위 분리는 검증하지 않는다. 같은 분석의 동시 피드백 제출도 최대 한 행만 생성하고 중복은 409로 거부한다.
- **SC-004**: 각 유형 상세를 두 번 조회했을 때 외부 분석·새 결과·쿼터 증가가 모두 0이다.
- **SC-005**: 기존 검증 회귀 사례가 모두 통과하고 실패 요청의 정상 결과는 0건이다.
- **SC-006**: 동일 입력 동시 성공 2회에서 각자의 결과와 서로 다른 ID를 받고 기초 정보는 중복되지 않는다.
- **SC-007**: 초기화 전 제공된 피드백 원본은 DB 전체 행·전체 컬럼·값과 100% 일치한다. 탈퇴 사용자 행 포함, 조인·가공·마스킹·필터 0건, 누락 0건이며 로컬 보관을 확인한다. 실제 DB의 탈퇴 사용자 피드백이 0건이면 정상이며 존재하지 않는 행을 생성·복원하지 않는다.
- **SC-008**: 공유 한도·동시 차감·원래 날짜 복원·자정 경계·커밋 후 응답 실패·관운/상세 미차감 사례가 현행 정책과 일치한다. 초기화 직후 기존 daily_api_usage는 0건이다.
- **SC-009**: 세 유형 총 건수·SAJU 원본/접근 건수·사용자별 유형 건수와 산정 기준이 모두 제공되고 같은 시점의 DB와 각 정의별로 일치한다. 추출 누락·불일치·운영자 미확인 상태에서 초기화 실행은 0회다.
- **SC-010**: 확인된 순서로 행 초기화 직후 대상 9개 테이블은 모두 0건이다. 새 스키마 적용 후 구형 전용 6개 테이블은 없고 새 분석/프로필/만세력/피드백/사용량은 0건이며 계정·인증 데이터 손실은 0건이다. 첫 신규 요청부터 정상 기록되고 관리자 통계는 saju 행 수와 일치한다.

- **SC-011**: 기본 프로필 미설정·저장·조회·기본값으로 분석·다른 정보로 분석·기본값 변경 사례가 통과한다. 기본값 저장의 만세력 생성·분석·차감은 0건이고 다른 정보 분석의 기본값 자동 변경은 0건이다. 기본값 변경으로 공유 프로필·과거 결과·진행 중 요청의 확정 입력이 바뀌지 않는다.

- **SC-012**: 전환 리허설에서 구형 전용 6개 테이블과 피드백 구형 대상 컬럼·FK·feedback_type이 없고 새 테이블·FK·유일 제약·인덱스가 설계와 일치한다. 운영과 로컬 모두 명시적인 DDL 적용 후 validate를 통과하고 첫 신규 분석·피드백 저장에 성공한다.
- **SC-013**: 빈 구조와 유형별 반복 분석·피드백 자료로 관리자 회원 목록·상세·사용량 조정·대시보드·피드백 목록·상세·통계를 검증한다. 회원 분석 건수와 당일·유형별 분석 집계는 해당 saju 행 수, 피드백 유형별 집계는 연결된 saju 유형별 피드백 행 수와 일치한다. 기존 권한·필터·페이지·응답 필드를 유지하고 구형 구조 조회는 0건이다.

- **SC-014**: 두 사용자가 같은 기초 정보를 공유한 상태에서 한 사용자가 탈퇴하면 계정은 soft delete·기본 참조 NULL·본인 피드백 0건이며 기존 saju와 공유 프로필·만세력 및 다른 사용자 자료는 그대로다. 원래 이름·이메일은 표시되지 않고 일반 사용자 접근은 거부된다. 관리자 건수·상세에는 남은 분석을 포함한다. 실패 시 탈퇴 DB 변경은 함께 롤백되고 탈퇴와 동시 쓰기는 정해진 커밋 순서로 처리한다.

## 전제

- 이번 작업은 설계 문서만 수정한다. 실제 SQL과 보고서 양식은 Git에서 제외된 로컬 문서(`specs/007-unify-saju-analysis/local/reset-runbook.md`)로 제공하며 저장소에는 포함하지 않는다. 실행 전 운영자 확인을 받는다.
- 기존 계정·보안·관리자 권한·검증·쿼터 날짜/실패 보상 정책은 초기화의 확정 영향을 제외하고 유지한다.
- 출생정보 키와 기존 정규화·허용 범위를 유지하고 새 역법·타임존·출생지 입력을 추가하지 않는다.
- 같은 입력의 결과 문구·점수가 같을 수 있지만 요청 실행·ID·저장은 독립적이다.
- 전환 이후 사용자에게 보이는 이력과 관리자 집계는 새 구조에서 성공한 요청만 대상으로 한다. 로컬로 제공한 과거 건수를 운영 통계로 다시 적재하지 않는다.
