## User Scenarios & Testing *(mandatory)*

### User Story 1 - 로그아웃/토큰 만료 후 재사용 불가 (세션 보안 하드닝) (Priority: P1)

사용자가 로그인, 세션 갱신, 로그아웃, 회원 탈퇴를 수행할 때 발급된 인증 토큰(Access/Refresh)이 정확한 시점에 무효화되어야 하며, 만료되거나 폐기된 토큰으로는 어떠한 보호 자원에도 접근할 수 없어야 한다. 또한 리프레시 토큰은 인증이 필요 없는 일반 API 요청에서는 노출되거나 검사되지 않아야 한다.

**Why this priority**: 현재 Access Token은 로그아웃/탈퇴 시 즉시 무효화할 방법이 없고, Refresh Token은 매 로그인마다 데이터베이스에 영구 누적되며, 검증 필터가 모든 경로에서 불필요하게 리프레시 토큰을 확인하고 있어 실질적인 보안 취약점이자 데이터 누적 장애다. 후속 과제(분산락 등)의 인프라 전제 조건이기도 하므로 최우선이다.

**Independent Test**: 로그인 후 로그아웃을 수행하고, 로그아웃 전 발급된 Access Token으로 보호된 API를 호출했을 때 거부됨을 확인한다. 별도로, 만료 시간이 지난 Refresh Token으로 갱신을 시도했을 때 거부되며 별도의 수동 정리 작업 없이 저장소에서 자동 제거됨을 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인된 사용자, **When** 로그아웃을 요청하면, **Then** 로그아웃 이전에 발급된 Access Token으로의 모든 후속 요청이 거부되고, 해당 Refresh Token으로는 더 이상 갱신할 수 없다.
2. **Given** Refresh Token의 유효 기간이 만료된 사용자, **When** 토큰 갱신을 시도하면, **Then** 요청이 거부되며 관리자가 별도로 데이터를 정리하지 않아도 만료된 토큰이 저장소에 남아있지 않다.
3. **Given** 회원 탈퇴를 완료한 사용자, **When** 탈퇴 전 발급받은 Access Token을 재사용하면, **Then** 요청이 거부된다.
4. **Given** 일반 보호 API(로그인/갱신/로그아웃이 아닌 경로)를 호출하는 사용자, **When** 요청에 Refresh Token 쿠키가 없거나 검증되지 않아도, **Then** Access Token만으로 정상 응답을 받는다(Refresh Token 검사는 갱신/로그아웃 경로에서만 수행됨).
5. **Given** 로그인/갱신에 성공한 사용자, **When** 응답을 받으면, **Then** Refresh Token은 HTTP 응답 본문이 아닌 HttpOnly 쿠키로만 전달된다.

### User Story 2 - API 외부 호출 실패 시 사용자 쿼터 보존 (Priority: P1)

궁합 분석(관계 매칭), 커리어 컨설팅(OpenAI 기반) 등 외부 분석 서비스를 호출하는 기능에서, 외부 서비스 장애나 일시적 오류로 분석이 실패하더라도 사용자의 일일 사용 쿼터가 소진 처리되어서는 안 된다.

**Why this priority**: 현재 외부 호출 실패 시에도 쿼터가 차감된 채 복구되지 않아, 사용자가 실제로 받지 못한 서비스에 대한 이용 횟수를 잃는 실질적 장애다. 이는 궁합 분석(FastAPI 호출 경로)뿐 아니라 커리어 컨설팅(OpenAI 호출 경로)에서도 동일한 구조(쿼터 차감 → 외부 호출)로 발생하며, OpenAI 호출은 타임아웃/응답 파싱 실패 시 재시도 로직도 우회되는 경우가 있어 실패 빈도가 더 높다.

**Independent Test**: 외부 분석 서비스(궁합 분석의 FastAPI 호출, 커리어 컨설팅의 OpenAI 호출 각각)가 실패를 반환하도록 만든 뒤 분석을 요청하고, 요청 실패 후 사용자의 남은 일일 쿼터가 요청 이전과 동일한지 확인한다. 반대로 분석이 성공하면 쿼터가 정확히 1회 차감되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 오늘 쿼터가 남아있는 사용자, **When** 외부 분석 호출이 실패하면, **Then** 사용자의 일일 쿼터는 요청 전과 동일하게 유지된다.
2. **Given** 오늘 쿼터가 남아있는 사용자, **When** 분석 요청이 성공적으로 완료되면, **Then** 쿼터가 정확히 1회 차감된다.
3. **Given** 동일 사용자가 동시에 여러 번 분석을 요청하는 상황, **When** 쿼터가 소진된 이후 추가 요청이 들어오면, **Then** 초과 요청은 거부되고 쿼터는 음수가 되지 않는다.
4. **Given** 이번 달 컨설팅 캐시가 없어 신규 OpenAI 호출이 필요한 사용자, **When** OpenAI 호출이 타임아웃되거나 응답 처리에 실패하면, **Then** 사용자의 일일 쿼터는 요청 전과 동일하게 유지된다(캐시 히트로 OpenAI 호출을 생략한 경우는 애초에 차감 대상이 아님).

### User Story 3 - 외부 데이터 제공자 일시 장애에 대한 자동 재시도 (Priority: P2)

기업 정보를 조회하는 기능에서, 외부 제공자의 일시적 서버 오류(5xx)가 발생했을 때 시스템이 자동으로 재시도하여 사용자에게는 가급적 정상 결과를 제공해야 한다. 반면 요청 자체가 잘못된 경우(4xx)는 재시도 없이 사용자에게 즉시 명확한 오류를 안내해야 한다.

**Why this priority**: 현재는 외부 제공자의 일시적 장애까지 즉시 사용자 오류로 변환되어, 재시도되었다면 성공했을 요청까지 실패로 끝난다.

**Independent Test**: 외부 기업 정보 제공자가 일시적으로 5xx를 반환하도록 만든 뒤 요청을 보내고, 시스템이 재시도 후 성공 결과를 반환하는지 확인한다. 이어서 4xx를 반환하도록 만들었을 때는 즉시 사용자 대상 오류로 응답하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 외부 기업 정보 제공자가 일시적으로 5xx 오류를 반환하는 상황, **When** 사용자가 기업 정보를 조회하면, **Then** 시스템은 자동으로 재시도하고, 재시도 중 정상 응답을 받으면 사용자는 성공 결과를 받는다.
2. **Given** 외부 제공자가 4xx(잘못된 요청/찾을 수 없음 등)를 반환하는 상황, **When** 사용자가 기업 정보를 조회하면, **Then** 재시도 없이 즉시 사용자에게 이해 가능한 오류가 반환된다.

### User Story 4 - 신뢰할 수 있는 출처만 API에 접근 (Priority: P2)

웹 애플리케이션은 사전에 승인된 출처와 헤더를 통해서만 API와 통신할 수 있어야 하며, 임의의 요청 헤더를 허용해서는 안 된다.

**Why this priority**: 현재 허용 헤더가 와일드카드로 열려 있어 불필요하게 공격 표면을 넓히고 있다.

**Independent Test**: 허용되지 않은 임의의 커스텀 헤더를 포함한 사전 요청(preflight)을 보냈을 때 거부되고, 인증/콘텐츠 타입 헤더만 포함한 요청은 정상 처리되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 화이트리스트에 없는 커스텀 헤더를 포함한 브라우저 요청, **When** 사전 요청(preflight)이 전송되면, **Then** 해당 헤더는 허용되지 않는다.
2. **Given** `Authorization`, `Content-Type` 헤더만 포함한 요청, **When** API를 호출하면, **Then** 정상적으로 처리된다.

---

### User Story 5 - 동시 요청에도 중복 없이 안전하게 자원 생성 (Priority: P2)

동일한 대상(예: 동일 사용자 프로필의 사주 분석 결과)에 대해 여러 요청이 동시에 들어오더라도, 정본 데이터가 중복 생성되거나 상태가 꼬이지 않고 하나의 요청만 실제 생성 작업을 수행해야 한다.

**Why this priority**: 기존 DB 제약조건 충돌 후 애플리케이션 재시도 방식은 예외 기반의 우회적 해결책으로, 원인 구분(무결성 위반 vs 동시성 경합)이 불명확해 오동작 위험이 있다.

**Independent Test**: 동일한 키에 대해 동시에 다수의 생성 요청을 보내고, 결과적으로 정본 데이터가 정확히 하나만 생성되며 나머지 요청은 그 정본을 정상적으로 참조/응답받는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 동일한 사용자 프로필에 대한 분석 요청이 동시에 여러 건 접수된 상황, **When** 모든 요청이 처리되면, **Then** 정본 데이터는 정확히 하나만 생성되고 모든 요청자는 동일한 정본 결과를 받는다.
2. **Given** 진짜 데이터 제약 조건 위반(예: 잘못된 참조값)이 발생한 상황, **When** 저장을 시도하면, **Then** 동시성 경합과 구분되는 명확한 오류로 처리된다.

---

### User Story 6 - 사주 정본 데이터의 소유권과 캐시 분리 (Priority: P3)

동일한 생년월일시 조합(사용자 프로필)에 대한 사주 분석 결과는 한 번만 계산되어 재사용되는 "정본"으로 취급되어야 하며, 어떤 사용자가 그 정본에 접근할 권한이 있는지는 별도로 관리되어야 한다. 이때 정본을 처음 조회/생성하는 행위 자체는 사용자의 일일 이용 쿼터를 소진시키지 않아야 한다.

**Why this priority**: 정본과 소유권이 뒤섞여 있으면 캐시 재사용 시 잘못된 권한 검증이나 불필요한 쿼터 차감이 발생할 수 있다. B1 항목이며 인프라(P1~P5) 이후 순서로 진행한다.

**Independent Test**: 서로 다른 두 사용자가 동일한 생년월일시 프로필로 분석을 요청했을 때 동일한 정본 결과를 재사용하면서도, 각자 자신의 상담 내역에서만 그 결과에 접근 가능한지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이미 계산된 정본이 존재하는 생년월일시 조합, **When** 다른 사용자가 동일 조합으로 분석을 요청하면, **Then** 재계산 없이 기존 정본을 재사용하여 응답한다.
2. **Given** 사용자 A가 접근 권한을 가진 정본, **When** 사용자 B가 자신의 권한 없이 해당 정본 기반 상담(피드백 등)에 접근을 시도하면, **Then** 접근이 거부된다.
3. **Given** 정본을 최초로 생성하는 요청, **When** 계산이 완료되면, **Then** 이 생성 자체만으로는 사용자의 일일 분석 쿼터가 차감되지 않는다.

### User Story 7 - 회원가입 시 태어난 시간(선택) 반영 (Priority: P3)

가입 시 생년월일은 필수로, 태어난 시간은 선택적으로 입력받을 수 있어야 한다. 태어난 시간을 입력하지 않은 사용자도 분석을 받을 수 있어야 하며, 이 경우 시간에 따라 달라지는 세부 결과 항목은 응답에서 제외되어야 한다.

**Why this priority**: 신규 요구사항으로, 사용자가 태어난 시간을 몰라도 서비스 이용에 지장이 없어야 하는 접근성 요구사항이다.

**Independent Test**: 태어난 시간 없이 가입한 사용자가 분석을 요청했을 때 정상적으로 결과를 받되, 시간 기반 세부 항목이 결과에 포함되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 태어난 시간을 입력하지 않고 가입한 사용자, **When** 분석을 요청하면, **Then** 요청이 거부되지 않고 정상적으로 처리된다.
2. **Given** 태어난 시간이 없는 사용자의 분석 결과, **When** 사용자가 결과를 확인하면, **Then** 시간에 따라 달라지는 세부 항목은 결과에 나타나지 않는다.
3. **Given** 태어난 시간을 입력하고 가입한 사용자, **When** 분석을 요청하면, **Then** 시간 기반 세부 항목을 포함한 전체 결과를 받는다.

### User Story 8 - 관리자 계정 활동에 대한 완전한 감사 추적 (Priority: P3)

관리자 로그인 시도는 성공/실패 여부와 관계없이 감사 로그로 기록되어야 하며, 이를 통해 비정상적인 관리자 계정 접근 시도를 사후에 추적할 수 있어야 한다.

**Why this priority**: 현재 관리자 인증 시도에 대한 감사 커버리지 공백이 있어, 보안 사고 발생 시 추적이 불가능하다.

**Independent Test**: 관리자 로그인을 성공/실패 각각 시도한 뒤, 두 경우 모두 감사 로그에 시도 결과가 기록되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 올바른 관리자 자격 증명, **When** 로그인에 성공하면, **Then** 성공 이벤트가 감사 로그에 기록된다.
2. **Given** 잘못된 관리자 자격 증명, **When** 로그인에 실패하면, **Then** 실패 이벤트가 감사 로그에 기록된다.

### User Story 9 - 코드베이스 구조 일관성 및 유지보수성 확보 (Priority: P4)

개발팀이 코드를 유지보수할 때, 패키지 구조·예외 계층·입력 검증·감사 로그 유틸리티·페이지네이션 방식이 일관된 규칙을 따라야 하며, 사용되지 않는 코드가 남아있지 않아야 한다.

**Why this priority**: 사용자에게 직접적인 영향은 없지만, 향후 장애/버그 발생 가능성을 낮추고 개발 생산성을 유지하기 위한 엔지니어링 품질 요구사항이다. 우선순위가 가장 낮아 인프라·버그 수정·데이터 모델 작업 이후 진행한다.

**Independent Test**: 정적 분석 및 코드 리뷰를 통해 경력 관련 컨트롤러/DTO가 지정된 패키지 하위에 위치하는지, 중복된 JWT 검증 로직이 제거되었는지, 필수 입력 필드에 검증 애노테이션이 존재하는지, 사용되지 않는 코드가 제거되었는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 커리어 관련(타이밍/궁합/상담/피드백) 컨트롤러와 DTO, **When** 코드베이스를 확인하면, **Then** 모두 일관된 패키지 하위에 위치한다.
2. **Given** 사용자용/관리자용 JWT 검증 필터, **When** 코드를 비교하면, **Then** 공통 검증 로직이 중복 없이 공유된다.
3. **Given** 필수 입력 값을 요구하는 요청 DTO(쿼터 조정, 궁합 분석의 시간 필드 등), **When** 해당 값 없이 요청을 보내면, **Then** 유효성 검증 오류로 거부된다.
4. **Given** 더 이상 사용되지 않는 상수/리포지토리 메서드/DTO/예외 클래스, **When** 코드베이스를 검색하면, **Then** 존재하지 않는다.
5. **Given** 트랜잭션 커밋 이후 완료 로그를 남기는 여러 관리자 기능, **When** 로그 기록 방식을 비교하면, **Then** 공통화된 방식을 따른다.

---

### Edge Cases

- 리프레시 토큰의 유효기간이 만료되기 직전에 여러 갱신 요청이 동시에 들어오면 어떻게 되는가? (하나의 요청만 성공하고 나머지는 일관되게 실패해야 한다.)
- 외부 분석/기업정보 제공자가 재시도 한도 내내 계속 5xx를 반환하면 어떻게 되는가? (최종적으로 사용자에게 일시적 오류로 안내되고, 쿼터는 차감되지 않아야 한다.)
- 커리어 컨설팅에서 이번 달 캐시가 없어 신규 OpenAI 호출이 발생했는데, 그 호출이 타임아웃되거나 응답 처리(파싱/검증)에 실패하면 어떻게 되는가? (쿼터는 이미 차감된 상태로 남지 않아야 하며, 요청 전 상태로 복원되어야 한다.)
- 이미 정본이 존재하는 생년월일시 조합에 대해 정본 삭제/데이터 정리 작업 중 하위 상담 이력이 참조하는 정본이 사라지면 어떻게 되는가? (하위 데이터는 참조 무결성이 깨지지 않도록 살아남는 정본을 가리켜야 한다.)
- 태어난 시간 없이 가입한 사용자가 이후 시간을 추가로 입력하면 어떻게 되는가? (다음 분석부터 시간 기반 세부 결과를 받을 수 있어야 한다.)
- 관리자 계정이 짧은 시간 내 반복적으로 로그인에 실패하면 어떻게 되는가? (모든 시도가 개별적으로 감사 로그에 남아 이상 탐지에 활용될 수 있어야 한다.)

## Requirements *(mandatory)*

### Functional Requirements

**세션/토큰 보안 (Redis, User Story 1)**

- **FR-001**: 시스템은 Refresh Token을 관계형 데이터베이스가 아닌 만료 시간(TTL)이 자동 적용되는 저장소에 보관하여, 만료된 토큰이 수동 정리 없이 자동으로 제거되도록 해야 한다.
- **FR-002**: 시스템은 로그아웃 또는 회원 탈퇴 시 발급되어 있던 Access Token을 즉시 무효화하여, 자연 만료 이전이라도 더 이상 사용할 수 없도록 해야 한다.
- **FR-003**: 시스템은 로그인/토큰 갱신에 성공하면 Refresh Token을 HTTP 응답 본문이 아닌 HttpOnly 쿠키로만 전달해야 한다.
- **FR-004**: 시스템은 로그아웃 시 Refresh Token 쿠키를 명시적으로 만료/삭제 처리해야 한다.
- **FR-005**: 시스템은 토큰 갱신 및 로그아웃 엔드포인트에서만 Refresh Token(쿠키)을 검사해야 하며, 그 외 일반 보호 API 경로에서는 Refresh Token의 존재 여부를 검사하지 않아야 한다.

**API 쿼터 무결성 (User Story 2)**

- **FR-006**: 시스템은 외부 분석 호출(궁합 분석의 FastAPI 호출, 커리어 컨설팅의 OpenAI 호출을 포함)이 성공적으로 완료된 경우에만 사용자의 일일 이용 쿼터를 확정 차감해야 한다.
- **FR-007**: 시스템은 외부 분석 호출(OpenAI 호출 포함)이 실패한 경우, 이미 차감된 쿼터가 있다면 이를 복원하거나 애초에 차감이 발생하지 않도록 보장해야 한다.
- **FR-008**: 시스템은 동시에 여러 요청이 들어와도 사용자의 일일 쿼터가 한도를 초과해 차감되지 않도록 해야 한다.

**외부 제공자 장애 대응 (User Story 3)**

- **FR-009**: 시스템은 기업 정보 제공자로부터 서버측 오류(5xx)를 받으면 사용자 대상 오류로 즉시 변환하지 않고 자동 재시도를 수행해야 한다.
- **FR-010**: 시스템은 기업 정보 제공자로부터 클라이언트측 오류(4xx)를 받으면 재시도 없이 사용자에게 이해 가능한 오류를 즉시 반환해야 한다.

**접근 제어 (User Story 4)**

- **FR-011**: 시스템은 브라우저 기반 API 요청에서 사전에 정의된 헤더(예: 인증, 콘텐츠 타입)만 허용하고, 그 외 임의의 헤더는 거부해야 한다.

**동시성 안전성 (User Story 5)**

- **FR-012**: 시스템은 동일 대상에 대한 동시 생성 요청이 들어와도 정본 데이터가 정확히 하나만 생성되도록 보장해야 한다.
- **FR-013**: 시스템은 동시성 경합으로 인한 재시도 상황과 실제 데이터 무결성 위반 상황을 구분하여 서로 다른 결과(성공적 재사용 vs 오류 반환)로 처리해야 한다.

**사주 정본/소유권 분리 (User Story 6)**

- **FR-014**: 시스템은 동일한 생년월일시 조합에 대해 하나의 정본 분석 결과만 유지하고, 동일 조합에 대한 이후 요청은 재계산 없이 기존 정본을 재사용해야 한다.
- **FR-015**: 시스템은 사용자와 정본 분석 결과 간의 접근 권한을 정본 자체와 분리하여 별도로 관리해야 하며, 권한이 없는 사용자는 다른 사용자의 정본 기반 상담/피드백에 접근할 수 없어야 한다.
- **FR-016**: 시스템은 정본을 최초로 생성하는 행위 자체만으로는 사용자의 일일 분석 쿼터를 차감하지 않아야 한다.
- **FR-017**: 시스템은 분석 유형을 나타내는 개념을 하나의 일관된 분류 체계로 통합하여 관리해야 하며, 동일한 개념에 서로 다른 두 가지 표현이 동시에 존재하지 않아야 한다.

**선택적 출생 시간 지원 (User Story 7)**

- **FR-018**: 시스템은 회원가입 시 생년월일을 필수로, 태어난 시간을 선택으로 입력받아야 한다.
- **FR-019**: 시스템은 태어난 시간이 없는 사용자에 대해서도 분석 요청을 정상 처리해야 한다.
- **FR-020**: 시스템은 태어난 시간이 없는 사용자의 분석 결과에서 시간에 따라 달라지는 세부 결과 항목을 제외하고 응답해야 한다.
- **FR-021**: 시스템은 태어난 시간이 없는 경우에도 분석에 필요한 내부 처리를 수행할 수 있어야 하며, 이때 시간 미입력으로 인한 처리 실패가 사용자에게 노출되지 않아야 한다.

**관리자 감사 추적 (User Story 8)**

- **FR-022**: 시스템은 관리자 로그인 시도의 성공 여부와 관계없이 각 시도를 감사 로그에 기록해야 한다.

**코드/구조 일관성 (User Story 9)**

- **FR-023**: 시스템은 경력 관련(타이밍/궁합/상담/피드백) 기능의 컨트롤러와 요청/응답 모델을 일관된 위치에 구성해야 한다.
- **FR-024**: 시스템은 사용자용/관리자용 인증 검증 로직 중 공통되는 부분을 중복 없이 공유해야 한다.
- **FR-025**: 시스템은 관리자 전용 데이터 접근이 관리자 전용 데이터 접근 경로만을 통해 이루어지도록 해야 한다.
- **FR-026**: 시스템은 컨트롤러 계층에 비즈니스 로직(세션 종료 처리, 사용자 식별 로직 등)을 두지 않고 서비스 계층에 위임해야 한다.
- **FR-027**: 시스템은 쿼터 조정 요청과 궁합 분석 요청의 필수 입력 항목이 누락된 경우 이를 거부해야 한다.
- **FR-028**: 시스템은 더 이상 사용되지 않는 상수, 리포지토리 메서드, DTO, 예외 클래스, 설정 클래스, 주석 처리된 미실행 코드를 유지하지 않아야 한다.
- **FR-029**: 시스템은 트랜잭션 완료 후 기록되는 완료 로그의 작성 방식을 여러 기능에서 일관되게 적용해야 한다.
- **FR-030**: 시스템은 비동기 처리 중 발생한 미처리 예외를 누락 없이 기록해야 한다.
- **FR-031**: 시스템은 도메인에서 발생하는 사용자 정의 예외를 하나의 일관된 예외 계층 구조로 관리하고, 각 예외 유형에 맞는 사용자 응답을 반환해야 한다.
- **FR-032**: 시스템은 데이터 조회 시 불필요하게 반복적인 하위 조회(N+1)가 발생하지 않도록 목록성 조회를 처리해야 한다.
- **FR-033**: 시스템은 서로 다른 목록 조회 기능에서 사용하는 페이지네이션 방식이 각각 왜 채택되었는지 확인할 수 있도록 근거를 남겨야 한다.

### Key Entities *(include if feature involves data)*

- **User / UserProfile**: 서비스 가입자와 그 인적 정보(생년월일 필수, 태어난 시간 선택)를 나타낸다. 하나의 사용자는 여러 사주 정본에 접근 권한을 가질 수 있다.
- **SajuResult (사주 정본)**: 특정 생년월일시 조합에 대해 단 한 번 계산되어 재사용되는 분석 결과. 특정 사용자에게 종속되지 않고 생년월일시 조합에 종속된다.
- **UserSajuAccess (사용자-정본 접근 매핑)**: 특정 사용자가 특정 사주 정본에 접근/소유할 권한이 있음을 나타내는 얇은 연결 정보.
- **CareerConsultation / Feedback**: 사주 정본을 기반으로 생성된 상담·피드백 이력. 소유권 검증은 정본이 아닌 매핑 정보를 통해 이루어진다.
- **AnalysisType**: 분석/피드백 항목의 종류를 나타내는 통합된 분류 값.
- **RefreshToken / AccessToken 무효화 기록**: 자동 만료(TTL)되는 세션 자격 증명과, 무효화된(로그아웃/탈퇴된) 토큰의 목록.
- **DailyApiUsage (일일 이용 쿼터)**: 사용자별 일일 분석 요청 가능 횟수와 소진 현황.
- **AdminAuditLog**: 관리자 계정의 인증 시도 및 주요 조작 행위에 대한 기록.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 로그아웃 또는 회원 탈퇴 직후 기존에 발급된 Access Token으로 보호된 API를 호출하는 100%의 시도가 거부된다.
- **SC-002**: 정상적인 로그인/로그아웃 활동 24시간 경과 후, 만료된 세션 자격 증명이 저장소에 수동 개입 없이 0건 남아있다.
- **SC-003**: 외부 분석 호출이 실패한 케이스에서 사용자 쿼터가 차감된 채 복구되지 않는 사례가 0건이다.
- **SC-004**: 외부 기업 정보 제공자의 일시적 5xx 장애 상황 재현 시, 재시도를 통해 최종적으로 성공 응답을 받는 비율이 이전 대비 향상된다.
- **SC-005**: 동일 대상에 대해 100건의 동시 생성 요청을 보내는 부하 테스트에서 정본 데이터가 정확히 1건만 생성된다.
- **SC-006**: 동일한 생년월일시 조합에 대한 반복 분석 요청 시 재계산 없이 기존 결과를 재사용하는 비율이 100%다.
- **SC-007**: 태어난 시간을 입력하지 않은 사용자의 분석 요청 성공률이 태어난 시간을 입력한 사용자와 동일한 수준으로 유지된다.
- **SC-008**: 관리자 로그인 시도(성공/실패) 기록이 감사 로그에서 100% 확인 가능하다.
- **SC-009**: 승인되지 않은 요청 헤더를 포함한 브라우저 사전 요청의 100%가 거부된다.
- **SC-010**: 코드베이스 내 사용되지 않는 것으로 확인된 상수/메서드/DTO/예외 클래스가 정리 작업 이후 0건이다.

## Assumptions

- Redis, Redisson 기반 분산락, MySQL 기반 통합 테스트(Testcontainers), 결정론적 `Clock` 빈 도입은 이해관계자가 이미 확정한 아키텍처 결정 사항이며, 후속 계획(`/speckit-plan`) 단계에서 이 결정을 그대로 반영한다.
- 정본 마이그레이션(중복 정본 제거 전 하위 데이터의 참조 갱신) 스크립트는 운영 데이터에 대한 일회성 작업으로, 버전 관리 대상 코드에는 포함하지 않는다.
- "정본 최초 생성이 쿼터를 소진하지 않는다"는 정책은 동일 생년월일시 조합에 대한 재사용 시에도 동일하게 적용되며, 캐시된 정본을 참조/조회하는 것 자체는 쿼터 대상이 아니다.
- 태어난 시간 미입력 시 내부적으로 처리되는 방식(가짜 시간 대입 등)은 구현 세부사항이며, 사용자에게 노출되는 것은 오직 "시간 기반 결과 항목의 존재 여부"뿐이다.
- 기존 사용자 중 이미 가입되어 있으나 태어난 시간 데이터가 없는 계정은 태어난 시간 미입력 사용자와 동일하게 취급된다.
- 관리자 감사로그, 완료 로그 등 로깅 관련 요구사항은 기존에 이미 부분적으로 존재하는 감사/로깅 체계를 확장하는 것을 전제로 한다.
- 페이지네이션 방식 통일은 이번 범위에서 강제하지 않으며, 기존 다양성을 유지하되 각 방식의 채택 근거만 명시한다.
