# Feature Specification: 커리어 분석 결과 JSON 저장 마이그레이션

**Feature Branch**: `006-career-json-migration`

**Created**: 2026-08-14

**Status**: Draft

**Input**: User description: "지금까지 정규화로 저장되어 있던 데이터베이스 사주 분석 결과(관운분석, 커리어컨설팅, 기업 궁합 분석)을 모두 JSON으로 마이그레이션, 단 기존 사용자의 분석 결과들은 모두 TRUNCATE 할 예정, 또한 실행하기 전 나한테 먼저 전에 진행했던 Open AI API 응답으로 온 값들은 원래 정합성 유지를 위해 검사를 했는데, JSON으로 바꾸면 어떻게 정합성 검사 할건지부터 제시해봐"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 분석 결과를 JSON 한 덩어리로 저장/조회 (Priority: P1)

백엔드 유지보수 담당자로서, 관운분석·커리어 컨설팅·기업 궁합 분석 결과를 자식 테이블 여러 개로 나눠 저장하는 대신 결과 레코드 하나당 JSON 컬럼 하나로 저장하고 싶다. 결과 필드는 조회 후 화면에 그대로 표시되는 용도로만 쓰이고 필드 단위 검색/집계에는 쓰이지 않으므로, 저장 구조를 단순화해 코드 유지보수 부담을 줄인다.

**Why this priority**: 세 도메인 모두에 적용되는 핵심 구조 변경이며, 이후 모든 관련 작업(정합성 검사 이관, 분산락 구현)의 전제 조건이다.

**Independent Test**: 관운분석/커리어 컨설팅/기업 궁합 각각에 대해 분석을 1회 요청하고, 저장된 결과를 조회했을 때 기존과 동일한 필드가 동일한 내용으로 표시되는지 확인하는 것으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 사용자가 기업 궁합 분석을 요청하고 외부 AI 응답을 정상적으로 받았을 때, **When** 결과가 저장되면, **Then** 결과는 단일 JSON 데이터로 저장되고 조회 시 기존 정규화 저장 방식과 동일한 필드·값이 화면에 표시된다.
2. **Given** 커리어 컨설팅 결과가 이미 JSON으로 저장되어 있을 때, **When** 같은 사용자가 같은 대상월에 대한 결과를 다시 조회하면, **Then** 재계산 없이 저장된 JSON 결과가 그대로 반환된다.
3. **Given** 신규 필드가 AI 응답 스키마에 추가되었을 때, **When** 해당 필드를 인식하도록 응답 파싱 대상(DTO)이 갱신된 뒤 저장되면, **Then** 별도의 데이터베이스 스키마 변경(컬럼 추가/마이그레이션) 없이 저장·조회되고, 저장 후 재조회했을 때 신규 필드 값이 저장 전과 동일하게 유지된다. (DTO 자체에 신규 필드를 인식시키는 코드 변경은 필요하다 — "DB 스키마 변경 불필요"이지 "코드 변경 불필요"가 아니다.)

### User Story 2 - AI 응답 정합성 검사를 저장 방식과 무관하게 유지 (Priority: P1)

백엔드 유지보수 담당자로서, OpenAI 응답이 불완전하거나 기대와 다른 값을 포함할 경우 지금처럼 저장 전에 걸러지길 원한다. 저장 구조가 정규화 테이블에서 JSON으로 바뀌더라도 검증 시점과 검증 항목은 동일하게 유지되어야 한다.

**Why this priority**: 정합성 검사가 느슨해지면 잘못되거나 불완전한 AI 응답이 그대로 사용자에게 노출될 위험이 있어, 저장 구조 변경과 동시에 반드시 보장되어야 한다.

**Independent Test**: 필수 필드가 누락되었거나 기대 대상월 집합과 다른 월 데이터를 포함한 AI 응답을 주입했을 때, 해당 응답이 저장되지 않고 오류로 처리되는지 확인하는 것으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** OpenAI 응답의 필수 텍스트 필드가 비어 있을 때, **When** 저장을 시도하면, **Then** 저장이 거부되고 사용자에게 오류가 반환되며 어떤 데이터도 저장되지 않는다.
2. **Given** 기업 궁합 분석 응답의 월별 전망(monthly forecast) 항목이 기대되는 대상월 집합과 일치하지 않을 때, **When** 저장을 시도하면, **Then** 저장이 거부된다.
3. **Given** 월별 전망 항목의 월(month) 값이 기대 대상월 집합에 속하지 않는 값(예: 범위를 벗어나거나 중복된 달)을 포함한 응답을 받았을 때, **When** 저장을 시도하면, **Then** 저장이 거부된다 (이 검사는 신규 도입이 아니라 기존 "기대 대상월 집합과 정확히 일치해야 한다"는 검사가 그대로 담당한다 — 대상월 집합 자체가 항상 1~12 범위이므로 범위를 벗어나는 값은 이 일치 검사에서 이미 걸러진다).

---

### User Story 3 - 기존 사용자 분석 결과 정리 (Priority: P2)

백엔드 유지보수 담당자로서, 아직 운영 중인 실사용자 데이터가 없는 개발 단계이므로 기존에 정규화 방식으로 저장된 관운분석·커리어 컨설팅·기업 궁합 결과를 모두 제거하고 새 JSON 저장 구조로 다시 시작하고 싶다.

**Why this priority**: 데이터 변환이 필요 없는 개발 단계 특성을 활용해 마이그레이션 복잡도를 낮추는 결정이며, User Story 1이 적용된 후에 실행되는 후행 작업이다.

**Independent Test**: 새 저장 구조 적용 후 기존 세 도메인의 결과 테이블을 조회했을 때 기존 데이터가 남아 있지 않고, 신규 분석 요청 시 정상적으로 새 결과가 생성되는지 확인하는 것으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 새 JSON 저장 구조가 적용되기 전 기존 방식으로 저장된 분석 결과가 존재할 때, **When** 마이그레이션이 적용되면, **Then** 기존 결과는 모두 제거되고 이후 신규 요청부터 새 구조로 저장된다.
2. **Given** 마이그레이션이 완료된 상태일 때, **When** 사용자가 이전에 조회했던 분석을 다시 요청하면, **Then** 기존 결과를 재사용하지 않고 새로 생성된 결과가 반환된다.

---

### Edge Cases

- OpenAI 응답이 아예 오지 않거나(null) 파싱 자체가 실패하는 경우: 기존과 동일하게 저장 시도 없이 즉시 오류 처리된다.
- 검증에 실패한 응답에 대해 재시도가 자동으로 이뤄지지 않는다(기존 동작 유지) — 네트워크/서버 오류만 재시도 대상이다.
- 동일 식별 키(예: 사용자+기업명+대상 직군+대상월, 또는 사용자+대상월)에 대한 동시 요청이 들어오는 경우: 저장 구조가 JSON으로 바뀌어도 동시 요청 중 하나의 결과만 최종 반영되고 나머지 요청자는 그 결과를 공유받는다(기존 동시성 제어 목적 유지).
- 생년월일시(출생 시각)를 입력하지 않은 사용자의 분석 요청: 시주(時柱) 기반으로만 산출되는 필드가 결과 JSON에서 제외되는 기존 동작이 유지된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 관운분석(사주 결과의 십신/지장간 분석), 커리어 컨설팅(CareerConsultation), 기업 궁합 분석(CompanyCompatibility) 결과를 각각 다수의 정규화된 자식 테이블이 아닌, 루트 결과 레코드당 하나의 JSON 데이터로 저장해야 한다.
- **FR-002**: 시스템은 결과 조회(중복 요청 판별)에 사용되는 식별 키 필드(예: 기업명+대상 직군+대상월, 사주 결과+상담월)를 JSON 안에 묻지 않고 별도의 조회 가능한 필드로 유지해야 한다.
- **FR-003**: 시스템은 AI 제공자(OpenAI) 응답을 저장하기 전에, 응답이 파싱된 직후 시점에서 필수 항목 존재 여부와 항목 간 일관성(예: 월별 전망 항목의 월 집합이 사전에 계산된 기대 대상월 집합과 정확히 일치하는지)을 검사해야 하며, 이 검사는 저장 형식(정규화 vs JSON)과 무관하게 동일하게 수행되어야 한다.
- **FR-004**: 시스템은 현재 데이터베이스 엔티티 제약(`@Min`/`@Max`)으로 수행되던 검사를 저장 전 단계에서 동등하게 보장해야 한다. 이 중 월(month) 값 검사는 이미 FR-003의 대상월 일치 검사가 포괄하므로 별도 코드 추가가 필요 없다. 점수(score/matchScore) 값은 AI 응답 필드가 아니라 시스템이 내부적으로 결정론적으로 계산하는 값이므로, 계산 로직 자체가 0~100 범위를 벗어나지 않도록 설계되어 있는 것으로 그 정합성을 보장한다(엔티티 컬럼이 사라지며 없어지는 것은 Hibernate 레벨의 방어적 재검증일 뿐, 값의 출처는 애초에 신뢰할 수 없는 외부 응답이 아니다).
- **FR-005**: 시스템은 정합성 검사에 실패한 AI 응답을 저장하지 않아야 하며, 사용자에게는 기존과 동일한 방식으로 오류를 반환해야 한다.
- **FR-006**: 시스템은 이번 변경 적용 시점에 기존에 저장되어 있던 관운분석·커리어 컨설팅·기업 궁합 분석 결과를 모두 제거해야 한다(운영 중인 실사용자 데이터가 없는 개발 단계이므로 데이터 변환 없이 삭제). 구조가 완전히 사라지는 자식 테이블은 삭제(DROP)하고, 컬럼 구조만 바뀌는 루트 테이블은 스키마 변경 후 기존 행을 비운다(TRUNCATE).
- **FR-007**: 시스템은 동일 식별 키에 대한 동시 요청 시 중복된 외부 AI 호출 및 중복 결과 생성을 방지하는 기존 동시성 제어 목적을 저장 구조 변경 이후에도 계속 충족해야 한다.
- **FR-008**: 시스템은 저장된 JSON 결과에 새로운 항목이 추가되는 경우에도 데이터베이스 스키마 변경 없이 저장 및 조회가 가능해야 한다.
- **FR-009**: 이번 변경에 대한 데이터베이스 마이그레이션 스크립트는 버전 관리 저장소에 포함하지 않으며, 스키마 변경은 운영자가 수동으로 적용한다.

### Key Entities *(include if feature involves data)*

- **관운분석 결과(사주 결과의 십신/지장간 분석)**: 사주 결과(`SajuResult`)에 딸린 십신 분포·지장간 상세 분석 데이터. 사용자·사주 결과 식별 정보는 별도 필드로, 나머지 분석 내용은 JSON으로 저장된다. (참고: 시기별 운세 판정 결과 자체를 담는 별도 결과 레코드는 이미 스칼라 컬럼 3개뿐이라 이번 마이그레이션 대상이 아니며 변경되지 않는다.)
- **커리어 컨설팅 결과(CareerConsultation)**: AI가 생성한 산업 추천, 강점/약점, 인터뷰 팁 등을 포함하는 상담 결과. 사용자·상담 대상월 식별 정보는 별도 필드로, 나머지 상담 내용(현재 14개 자식 항목으로 나뉘어 있는 데이터)은 JSON으로 저장된다.
- **기업 궁합 분석 결과(CompanyCompatibility)**: 특정 기업·직군에 대한 궁합 분석 결과. 기업명·대상 직군·대상월 식별 정보는 별도 필드로, 나머지 분석 내용(현재 8개 자식 항목으로 나뉘어 있는 데이터)은 JSON으로 저장된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 마이그레이션 이후 생성된 관운분석·커리어 컨설팅·기업 궁합 분석 결과는 마이그레이션 이전과 동일한 항목·내용을 손실 없이 사용자에게 표시한다.
- **SC-002**: 정합성 검사를 통과하지 못하는 AI 응답은 마이그레이션 이후에도 100% 저장되지 않고 거부된다.
- **SC-003**: 동일 식별 키에 대한 동시 요청이 발생해도 최종적으로 정확히 하나의 결과만 저장되고, 모든 요청자가 동일한 결과를 받는다.
- **SC-004**: AI 응답 스키마에 새 항목이 추가될 때 이를 저장·표시하기 위한 데이터베이스 스키마 변경 건수는 0건이다.
- **SC-005**: 마이그레이션 적용 후 기존에 저장되어 있던 세 도메인의 분석 결과는 0건 남아있다.

## Assumptions

- 아직 운영 중인 실사용자 데이터가 없는 개발 단계이므로, 기존 데이터를 새 구조로 변환하는 마이그레이션 스크립트 없이 삭제 후 재생성하는 방식을 전제로 한다.
- 데이터베이스 스키마 변경 스크립트는 프로젝트 관례에 따라 버전 관리에 커밋하지 않고 운영자가 수동으로 적용한다.
- 관운분석은 OpenAI가 아닌 별도 외부 분석 서비스(FastAPI 기반 규칙 분석)를 사용하지만, 저장 구조(JSON화)는 동일하게 적용된다.
- 저장 전 정합성 검사 로직(필수 항목 검사, 기대 대상월 집합 일치 검사)은 기존에 이미 정규화 엔티티 매핑 이전 단계(AI 응답 파싱 직후)에서 수행되고 있었으므로, 이번 변경으로 새로 도입되는 검사가 아니라 기존 검사 지점을 그대로 유지하는 것이다.
- 동시 요청에 대한 중복 방지(분산락) 작업은 이번 스펙의 구현 범위가 아니며 별도로 진행되지만, 이번 저장 구조 변경이 그 필요성을 없애지 않는다는 전제로 순서를 조율한다.
