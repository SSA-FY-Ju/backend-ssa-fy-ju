## 3. 초기화 전 제공할 자료

### 피드백 원본 전체

user_satisfaction_feedback의 모든 행·모든 컬럼을 그대로 내보낸다. 조인·가공·마스킹·필터를 하지 않는다. 탈퇴 사용자 행, 작성자나 대상 연결에 문제가 있는 행도 포함한다. ORM의 soft delete 제한이나 사용자 상태 조건을 적용하지 않는다.

컬럼명·컬럼 순서·값·NULL·문자열 줄바꿈·시각 정밀도가 손실되지 않는 로컬 원본 자료를 제공한다. 새 피드백 FK 형태로 변환하지 않고 기존 두 유형별 FK 컬럼을 포함한 원본 전체를 유지한다. 집계 결과나 설명을 원본의 추가 컬럼으로 합치지 않는다.

탈퇴 시 기존 서비스가 피드백을 삭제하므로 실제 DB에 탈퇴 사용자 피드백이 0건이어도 정상이다. 존재하는 행을 빠짐없이 제공한다는 뜻이며, 이미 삭제된 행을 복원·생성하지 않는다. 테스트 자료에는 해당 행을 넣어 필터가 없음을 검증한다.

전체 DB 백업·복구 자료와 복구 리허설 사본에도 피드백 원본과 동일한 접근 제한·저장 암호화·외부 동기화 금지·로컬 접근 감사 기록·보존 기간·기간 종료 후 안전한 파기 및 파기 확인을 적용한다. 복제 DB에 복원한 데이터와 내보낸 사본도 포함하며, 검증·복구에 필요한 동안은 보존하고 사용을 마친 사본과 암호화 키의 안전한 폐기를 확인한다.

로컬 피드백 원본은 탈퇴 사용자 행을 포함한 모든 행·모든 컬럼을 마스킹 없이 추출한다. 지정 운영자만 접근하도록 파일·디렉터리 권한을 제한하고 저장 암호화를 적용하며 외부 동기화·자동 업로드를 금지한다. 접근자·시각·행위를 개인정보 원문 없이 로컬 감사 기록에 남긴다. 추출 전에 접근 권한자·보존 기간·파기 책임자를 정하고, 기간 종료 후 원본·사본의 파기와 확인자·시점을 기록한다. 추출 직후 원본 파일의 SHA-256 체크섬을 기록하고 DB 대조 전후 동일함을 확인해 대조 결과의 무결성을 보장한다. 체크섬은 DB 전수 대조를 대체하지 않는다.

### 분석 건수와 산정 기준

| 지표 | 전체 범위와 기준 |
|---|---|
| SAJU 원본 총수 | saju_result 모든 행 수 |
| CAREER_CONSULTATION 총수 | career_consultation 모든 행 수 |
| COMPANY_COMPATIBILITY 총수 | company_compatibility 모든 행 수 |
| SAJU 사용자 접근 총수 | user_saju_access 모든 행 수. 원본 총수와 별도 제공 |

각 사용자와 유형을 구분하고 없는 유형은 0으로 표시한다. 탈퇴 사용자도 원래 ID로 포함한다. 계정 조인 때문에 원본/접근 행이 빠지지 않게 하고 미연결 항목은 제외하지 않고 별도 표기한다. 완료 상태·기간·탈퇴 여부로 필터하지 않는다.

보고서에는 어느 테이블의 무엇을 셌는지 위 기준을 함께 적는다. 사용자별 컨설팅 수는 공유 접근 기준이며 실제 요청 횟수를 뜻하지 않는다. SAJU 접근 총수는 원본 총수와 다르고, 공유 컨설팅의 사용자별 합계도 원본 총수와 다를 수 있다. 미연결 원본 수와 차이의 이유를 적어 서로 다른 정의의 합계를 억지로 같게 만들지 않는다.

## 4. 전환 순서

**분석 쓰기 중단 → 피드백 원본·건수 추출 → 추출 건수와 DB 건수 대조 → 운영자 확인 → 초기화 → 새 스키마 적용 → 배포**

### 1단계: 분석 쓰기 중단

추출 시작부터 새 스키마 DDL 적용·validate 통과·호환 애플리케이션 배포 완료까지 구형 애플리케이션 전체 중지 또는 사용자·관리자의 읽기·쓰기 트래픽 전체 차단을 유지하고 진행 중 조회·쓰기를 모두 종료한다. 쓰기 경로만 차단하는 방식은 허용하지 않는다. DDL 적용 직전부터 배포·스키마 검증 완료까지 AnalysisHistoryRepository와 관리자 조회를 포함한 구형 테이블 접근이 실행되지 않음을 확인하며, 조회·쓰기 차단을 보장할 수 없으면 초기화를 중단한다. 차단 방법은 운영자가 선택하며 별도 차단 기능 개발은 범위에 포함하지 않는다. 예정된 차단 해제 전 일반 트래픽 차단이 풀리거나 허용된 smoke 외 쓰기가 발생하면 즉시 전환을 중단한다. 파괴적 초기화·DDL 시작 전이면 차단을 복구한 뒤 원본·건수를 재추출·대조하고 운영자 재확인을 받는다. 파괴적 초기화·DDL을 시작한 이후에는 쓰기를 중지하고 구형 앱의 조회 차단도 유지한 채 실제 DB 상태·적용된 문장과 검증된 백업·복구 자료를 확인한다. 신규 기록 손실을 검토하고 운영자 확인 후 복구·재검증하며, 초기화 전 절차처럼 자료를 단순 재추출하거나 자동 재삭제하지 않는다. 검증 전 백업 덮어쓰기를 금지한다. 인증 데이터는 삭제하지 않는다. 정지 시점·대상 DB·실제 테이블/컬럼/FK를 확인한다.

운영자 확인 전에 대상 DB 전체 백업을 로컬에 확보하고 복구 가능성을 검증하며, 복제 DB에서 해당 백업의 복구 리허설을 완료하고 결과를 로컬에 기록해야 한다. 백업·복구 검증·리허설 결과 중 하나라도 없거나 실패하면 초기화를 중단한다. 피드백 원본·건수 자료만으로 전체 분석을 복구할 수 있다고 간주하지 않는다.

### 2단계: 피드백 원본·건수 추출

Git에서 제외된 로컬 실행 문서의 내보내기·건수 조회 SQL을 사용자가 직접 실행한다. 위 §3의 원본과 모든 지표를 같은 쓰기 중단 시점 기준으로 로컬에 제공한다. 원본 전체와 별도 건수 보고서의 로컬 경로·추출 시점·대상 DB를 운영자가 확인할 수 있게 한다. 개인정보 원문을 업무 로그나 대화에 출력하지 않는다.

### 3단계: 추출 건수와 DB 건수 대조

원본 파일의 행 수가 user_satisfaction_feedback 전체 행 수와 같고 모든 컬럼·값이 변형 없이 들어 있는지 확인한다. 탈퇴 사용자 행과 NULL도 확인한다. 유형별 원본 수·접근 수·사용자별 유형 수는 각 산정 정의대로 DB와 대조한다. 공유 때문에 원본 수와 사용자별 합계가 다른 경우 그 차이를 설명하고 미연결 원본을 누락하지 않았는지 확인한다.

단일 테이블 원본 제공에는 조인·필터가 없어야 한다. 집계에는 필요한 분석/접근 연결만 사용하며 계정 상태로 제외하지 않는다. 파괴적 초기화·DDL 전 차단이 해제되거나 쓰기가 발생하면 즉시 중단하고 차단 복구 후 자료 재추출·대조와 운영자 재확인을 거친다. 추출 누락·변형·건수 불일치가 있어도 초기화하지 않고 자료를 재추출·대조한다.

### 4단계: 운영자 확인

운영자가 다음을 확인한 뒤 명시적으로 초기화 진행을 확인한다.

- 로컬 원본 전체와 건수·산정 기준을 제공받았고 DB 대조가 완료됐다.
- 대상 DB 전체 백업·복구 가능성 검증·복구 리허설이 완료됐고 로컬 결과 기록을 확인했다.
- 추출부터 새 스키마 DDL 적용·validate 통과·호환 애플리케이션 배포 완료까지 구형 앱 전체 중지 또는 읽기·쓰기 트래픽 전체 차단과 진행 중 조회·쓰기 종료가 보장된다.
- 삭제 대상에 분석·피드백·프로필·일일 사용량 전체가 포함된다.
- 계정·인증은 유지되고 과거 이력·분석 URL은 사라지며 당일 쿼터가 재설정된다.

확인이 없으면 다음 단계로 진행하지 않는다. 이번 문서 수정 요청이나 이전의 보존 방식 결정은 이 실행 확인을 대신하지 않는다. 확인한 자료·시점·범위는 개인정보 원문 없이 로컬 운영 기록에 남긴다.

### 5단계: 초기화

운영자 확인 후 Git에서 제외된 로컬 실행 문서의 실제 대상용 초기화 SQL을 사용자가 직접 실행한다. 검토한 FK 순서로 지정된 모든 행을 삭제하고 계정·인증 데이터는 변경하지 않는다. 실패하거나 완료 범위가 불분명하면 다음 단계로 넘어가지 않고 상태·복구를 확인한다. 확인 없이 자동으로 재삭제하지 않는다.

삭제 대상이 0건인지 확인한다. 계정·인증 자료는 정지 기준 자료와 대조해 손실·의도치 않은 변경이 없는지 확인한다. 실제 DML/DDL의 범위와 복구 가능 여부는 전달된 SQL 및 리허설 결과를 기준으로 확인한다.

### 6단계: 새 스키마 적용

빈 user_profile/manse/saju/피드백 구조를 적용한다. 만세력 계산 데이터는 ManseData record의 data_json 한 컬럼이며 모든 saju.manse_id는 NOT NULL이고 실제 분석 프로필은 manse를 경유하며 saju의 중복 프로필 FK는 없다. 분석 ID는 숫자 ID, 피드백 대상 FK는 UNIQUE인 saju_id 하나이며 분석당 0..1개다. 피드백의 별도 유형 컬럼·요청 필드 없이 saju.analysis_type으로 허용 여부를 검증한다. 구형 유형별 피드백 FK나 과거 데이터용 메타데이터·매핑·예외 구조는 남기지 않는다. 사용량 테이블도 빈 상태다. 계정·인증 테이블과 데이터는 유지한다.

구형 스키마 초기화를 완료한 뒤 `users.user_profile_id`를 NULL 허용 FK로 추가한다. 유지된 모든 계정은 기본 프로필 NULL로 시작하고 계정·인증 필드는 유지한다. 기본 참조는 UNIQUE가 아니며 삭제 연쇄 전파를 두지 않는다. 구형 초기화 SQL 실행 전에 이 FK를 추가하지 않는다.

구형 전용 6개 테이블은 DROP한다: user_saju_access, career_consultation, career_fortune, saju_full_data, company_compatibility, saju_result. 빈 user_profile·daily_api_usage는 재사용한다. 먼저 피드백의 구형 대상 FK를 제거하고 두 대상 컬럼·feedback_type을 삭제한다. 새 manse·saju 생성, 피드백 saju_id·FK·UNIQUE·user_id NOT NULL, 사용자 기본 참조와 인덱스를 적용한다. 실제 FK 이름·참조 자료형은 대상 DB와 대조하며 계정·인증 값을 변경하지 않는다.

구현 담당자가 제외된 로컬 reset-runbook.md의 f절에 CREATE·ALTER·DROP 및 검증 SQL을 작성하고 최종 엔티티와 동기화한다. 운영자는 실제 스키마 대조·복제 DB 리허설 후 e절 초기화 완료를 확인하고 f절을 실행한다. DDL은 e절 트랜잭션과 분리하며 암묵적 커밋 때문에 전체 ROLLBACK을 전제로 하지 않는다. 실행 오류 시 즉시 중지하고 적용된 문장·실제 스키마·백업으로 복구를 검토한다. IF EXISTS 등으로 스키마 차이나 부분 실패를 숨기지 않는다.

운영의 validate는 DDL을 대신하지 않는다. 로컬 프로필의 update에도 정리를 맡기지 않는다. 로컬 역시 계정 유지가 필요한 기존 DB에서는 동일한 사전 제공·확인·초기화·DDL을 적용한다. 새 애플리케이션 첫 기동 전 운영은 JPA_DDL_AUTO=validate를 확인하고 로컬은 명령행 --spring.jpa.hibernate.ddl-auto=validate로 update를 덮어써 검증한다. 기존 엔티티로 새 스키마에 기동하거나 새 엔티티의 update로 전환을 먼저 시도하지 않는다. JPA 검증과 별도로 구형 6개 테이블·세 피드백 컬럼·구형 FK 부재 및 새 컬럼·FK·유일 제약·인덱스를 확인한다.

### 7단계: 배포

구형 앱 전체 중지 또는 읽기·쓰기 트래픽 전체 차단을 유지한 채 새 코드의 스키마 validate 통과 후 호환 애플리케이션을 배포한다. 일반 사용자·관리자의 읽기·쓰기 차단과 구형 앱 중지를 유지한 채 호환 앱에만 검증 접근을 허용한다. 읽기 smoke로 기존 계정 로그인·빈 개인/관리자 이력·없는/타인/유형 불일치 ID 404를 확인한 뒤 테스트 계정의 제한된 쓰기 smoke로 신규 분석·피드백·기본 프로필·관리자 경로와 공유 쿼터를 검증한다. DDL 적용·validate 통과·호환 앱 배포와 필수 smoke 검증이 모두 성공한 경우에만 일반 읽기·쓰기 차단을 해제하며, 실패하면 차단을 유지하고 quickstart.md §6의 복구 절차를 따른다. 공통 application.yaml의 spring.datasource.hikari.data-source-properties.useAffectedRows=true 적용과 운영 DB_URL의 충돌 옵션 부재를 확인한다. 쿼터 smoke test에서 컨설팅·궁합 합산 세 번 성공 후 네 번째 요청이 429인지 확인한다. 기존 계정 로그인·빈 마이페이지·관리자 0건·없는/타인 분석 ID 404를 확인한 뒤 테스트 계정으로 첫 신규 분석을 검증한다. 새 프로필/만세력/분석이 생성되고 숫자 ID로 조회·허용 피드백이 연결되는지 확인한다. 배포 smoke test가 새 행을 만들기 전의 빈 상태 증거와 이후 검증 결과를 구분한다.

## 6. 운영 및 중단 기준

배포 후 기존 지연·오류·쿼터 보상 실패 관찰을 유지한다. 로컬에 제공하는 원본 자료를 제외한 로그에는 출생정보·프롬프트·결과 전문을 쓰지 않는다.

예정된 차단 해제 전 일반 트래픽 차단이 풀리거나 허용된 smoke 외 쓰기가 발생하면 즉시 전환을 중단한다. 파괴적 초기화·DDL 시작 전이면 차단을 복구한 뒤 원본·건수를 재추출·대조하고 운영자 재확인을 받는다. 파괴적 초기화·DDL을 시작한 이후에는 쓰기를 중지하고 구형 앱의 조회 차단도 유지한 채 실제 DB 상태·적용된 문장과 검증된 백업·복구 자료를 확인한다. 신규 기록 손실을 검토하고 운영자 확인 후 복구·재검증하며, 초기화 전 절차처럼 자료를 단순 재추출하거나 자동 재삭제하지 않는다. 검증 전 백업 덮어쓰기를 금지한다. 원본/집계 파일은 자동 재적재 자료가 아니다.

작업 목록은 생성 완료됐으며 다음 단계는 미완료 구현 작업 수행이다. 빈 모델·숫자 ID·런타임 기능·회귀·로컬 실행 문서로 SQL 제공 및 운영 확인 절차를 작업화하며 과거 분석 변환 작업을 생성하지 않는다.
